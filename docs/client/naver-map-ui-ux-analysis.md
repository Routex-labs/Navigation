# 네이버지도 UI/UX 분석과 개선 항목 (v2)

네이버지도 실제 화면을 캡처해 우리 클라이언트와 비교하고, 거기서 도출한 작업 항목을
정리한다. [지도·상세 UI 개선 계획 (v1)](map-ui-redesign-plan.md)이 **지도 렌더링**
(폰트·팔레트·마커·경로선)을 다뤘다면, 이 문서는 **정보 구조와 목록·시트 UX**를 다룬다.
겹치는 항목은 본문에서 v1 번호로 연결한다.

- 설명·주석·커밋은 한국어, 코드·식별자는 영어 (AGENTS.md 규칙).
- v1과 같은 원칙을 따른다 — **무엇을 왜 바꾸는지**와 **무엇이 충족되면 맞다고 볼지**를
  담고, 정상 동작보다 **실패 조건을 먼저** 적는다.

---

## 캡처 출처와 한계

2026-08-03, `map.naver.com/p` **데스크톱 웹**을 Chrome에서 직접 조작하며 6개 화면을
캡처했다. 검색어는 `더현대서울`이다.

| # | 화면 | URL |
|---|---|---|
| 1 | 지도 홈 (검색 전) | `/p?c=...` |
| 2 | 검색어 입력 중 (자동완성) | `/p?c=...` |
| 3 | 검색 결과 목록 | `/p/search/더현대서울` |
| 4 | 장소 상세 | `/p/entry/place/...` |
| 5 | 장소 상세 — 홈 탭의 내부시설 섹션 | `/p/entry/place/...` |
| 6 | 장소 상세 — 내부시설 전용 탭 | `/p/entry/place/...` |

**한계 두 가지를 먼저 적는다.**

1. **데스크톱 웹이다.** 우리가 만드는 건 모바일 앱이다. 좌측 세로 rail은 모바일에서
   하단 탭바로 내려오므로 **항목 구성**은 그대로 읽을 수 있지만, **여백·크기·터치 타깃**은
   이 캡처에서 가져오면 안 된다. 모바일 앱 캡처는 아직 없다.
2. **네이버 도메인이 계정 안전 정책으로 차단돼 있다.** 에이전트가 직접 브라우징할 수
   없어 사람이 조작하고 캡처를 전달하는 방식으로 진행했다. 추가 화면이 필요하면 같은
   방식이어야 한다.

## 벤치마크 경계 — 네이버에 없는 것

**네이버지도에는 실내 층 UI가 없다.** 5·6번 화면(내부시설 497건)에서 확인했다.
홈 탭의 섹션과 **내부시설 전용 탭 양쪽 모두** 그렇다 — 전용 탭이라 층으로 나뉠 법한데
그렇지 않았다.

- 목록 항목 어디에도 층 표기가 없다. `마사비스 / 베이커리 / 블로그 리뷰 151`처럼
  이름·업종·리뷰수만 있다.
- 필터 pill이 `음식 130` `쇼핑 290` `즐길거리 4` `기타 73`으로 **업종 기준**이다.
  층 기준 필터가 없다.
- 층은 검색 결과의 주소 문자열에 섞여 나올 뿐이다 (`여의대로 108 지하1층`,
  `108 B2 EQL`). 1급 정보가 아니다.

즉 네이버는 건물 안 매장을 **평면 POI 목록**으로 다루지, 층을 가진 공간으로 다루지
않는다. 따라서 **층 선택기·층 전환·다층 경로는 베낄 대상이 없고 우리가 설계해야
한다.** 이 문서의 제안을 층 UI에 그대로 확장하지 말 것.

## 벤치마크 경계 — 있어도 넣으면 안 되는 것

네이버 화면에는 있지만 **이 저장소가 코드로 금지**하는 정보가 있다.
`backend/resources/store_details/_schema.json`의 `forbidden_labels`:

```
"영업시간", "영업 시간", "운영시간", "운영 시간",
"전화", "전화번호", "대표번호", "연락처", "문의", "평점", "리뷰"
```

`backend/app/repositories/place_details.py`가 시드 적재 **전에** 검증 실패시킨다.
과거에 출처 없는 영업시간·대표번호가 응답에 실려 나간 사고가 있어 막아둔 규칙이다
(v1 「보류 항목」 참조).

따라서 아래는 **캡처에 보이더라도 지금 구현하면 안 된다.**

| 네이버 화면 요소 | 우리 상태 |
|---|---|
| `영업 전 · 10:30에 영업 시작` | 금지 — 데이터 출처 결정 선행 (v1 보류 항목 B안) |
| `휴무일 · 08/10(월)` | 금지 — 같음 |
| `1588-3650 복사` | 금지 |
| `리뷰 12.6만` · `블로그 리뷰 1,197` | 금지 |

**거리·층·업종은 제한 없다.** 우리가 그래프에서 직접 계산하거나 이미 보유한 값이다.

## 화면별 관찰

### 1. 지도 홈 — 빈 상태가 콘텐츠로 채워져 있다

검색 전인데도 `계양구 계양2동` → 광고 → `Smart Around` → `주변` 추천 캐러셀이 이어진다.
우리 `SearchPanel`의 `idle`은 안내 문구 한 덩어리뿐이다
(`search_panel.dart:542`).

부수 관찰:

- 검색창에 **그림자가 없다.** 초록 테두리 2px로만 강조한다.
- 지도 컨트롤은 **우측 세로 스택**이고, 아이콘 아래에 **라벨이 붙는다**
  (`테마`·`저장`·`거리뷰`·`반경`·`면적`·`거리`).
- 필터를 칩으로 늘어놓지 않는다. 섹션 헤더 우측에 `아침/오전 시간대` `추천순 ⌄`처럼
  **텍스트 + chevron**으로 접는다.

### 2. 검색어 입력 중 — 두 종류를 한 목록에

| 구간 | 아이콘 | 구성 |
|---|---|---|
| 상단 3줄 | 돋보기 | 검색어 제안. 전체가 파란 텍스트 (`더현대서울 맛집`, `더현대서울 카페`) |
| 이하 | 핀 | 장소. 이름(매칭 구간만 파랑) + 우측 회색 카테고리 + 2행 주소 |

- **매칭 구간만 하이라이트한다.** `현대백화점 **더현대 서울**`, `죠죠 **더현대서울**점`.
  왜 이 결과가 나왔는지를 색으로 설명한다.
- 카테고리는 **우측 회색 텍스트**다 (`백화점`·`종합패션`·`일식당`). 카테고리별 아이콘을
  쓰지 않는다. 좌측 아이콘은 돋보기/핀 **2종뿐**이다.
- 층이 주소 줄에 녹아 있다 (`여의대로 108 지하1층`).
- 후보가 넓을 때 **되묻지 않는다.** 질문 대신 제안 3줄을 얹고 끝낸다.

### 3. 검색 결과 목록 — 행에서 바로 길찾기

```
현대백화점 더현대 서울  백화점        ┌──────┐
영업 전 · 10:30에 영업 시작          │ 썸네일 │
08/10(월) · 휴무                    └──────┘
17km · 서울 영등포구 여의도동 ⌄
[ 출발 | 도착 ]  (핀)
```

- **`출발 | 도착`이 결과 행에 직접 있다.** 상세로 들어가지 않고 목록에서 경로가 시작된다.
- 거리가 **볼드**, 주소는 회색. 거리가 가장 강한 판단 기준이다.
- 지도에 **번호 원형 핀**이 찍히고, 선택 항목은 **연회색 배경**으로 전체가 강조된다.
  목록과 지도가 양방향으로 연동된다.
- 상단에 `위치 표기 없는 업체 보기` 체크박스 — 좌표 없는 항목을 필터로 분리한다.

### 4. 장소 상세 — 액션이 스크롤에 따라 이동한다

초기 상태 순서: 제목 → `백화점 · 리뷰 12.6만` → 영업 상태 → **액션 pill 가로 줄** →
사진 캐러셀 → 탭 바 → 본문.

스크롤하면:

- 헤더가 `< 제목 ☆ ✕` 한 줄로 압축되고 탭 바만 sticky로 남는다.
- **액션 pill이 화면 하단 고정 바로 내려온다.** 어느 스크롤 위치에서도 길찾기가 닿는다.

구성 세부:

- 액션은 `출발`(옅은 파랑) → `도착`(채운 파랑) → `거리뷰` → `공유` → `알림` 가로 스크롤.
- **저장(☆)은 액션 줄이 아니라 헤더 우상단**에 있다. 뒤로(`<`)와 닫기(`✕`)가 둘 다 있다.
- 정보 리스트는 `아이콘 + 값 + ⌄`이고, 주소 **바로 아래**에
  `⑤ 여의나루역 1번 출구에서 466m` — "어디인가" 다음에 "어떻게 닿는가"가 온다.
- 길어지면 `정보 더보기 >`로 접는다.

### 5·6. 내부시설 — 검색 결과와 같은 행을 재사용

홈 탭의 섹션은 개수와 `>` 링크를 얹은 요약이고, 전용 탭은 같은 목록의 전체판이다.

```
홈 탭 섹션      내부시설 497 >
                [음식 130] [쇼핑 290] [즐길거리 4] [기타 73]

전용 탭          [N예약] │ [음식 130] [쇼핑 290] [즐길거리 4]  >
```

- 개수를 pill 안에 넣는다. 우리 `CategoryCount`와 같은 데이터 형태다.
- 카테고리 필터가 **지도 위가 아니라 장소 상세 시트 안**에 있다.
- **전용 탭에서 필터가 두 무리로 나뉜다.** `N예약`(속성 필터)이 맨 앞에 오고
  **세로 구분선**으로 카테고리 필터와 분리된다. 줄은 가로 스크롤이고 끝에 `>`가 붙는다.
  성격이 다른 필터를 한 줄에 두되 섞이지 않게 하는 방법이다.
- 항목 구성이 검색 결과와 동일하다. 썸네일 우하단에 사진 개수 뱃지(`12`·`35`),
  이름 뒤에 `N예약`·`톡톡` 초록 뱃지, 카테고리는 이름 뒤 인라인 회색.
- 층 정보 없음 (위 「벤치마크 경계」 참조).

## 도출 작업

v1과 번호가 섞이지 않도록 알파벳으로 매긴다.

### A. 검색 결과 행 정보 구조 <sub>완료</sub>

```
c61c48d feat: 검색 결과 한 줄에 검색어 강조와 업종을 함께 보여준다   (A-1)
        feat: 검색 결과에 현재 위치 기준 거리와 도보 시간을 붙인다     (A-2)
```

**A-1(표현)과 A-2(계산)를 나눠 커밋했다.** 앞은 `_storeTile` 안에서 끝나는 표현
변경이고, 뒤는 건물 그래프 로드 + 다익스트라라 성격이 다르다.

**A-2에서 정한 것 — 다익스트라를 결과마다 돌리지 않는다.** 다익스트라는 한 번
끝까지 돌면 모든 노드까지의 최솟값을 함께 얻는다. 결과 30건에 30번 돌리는 대신
[`reachableFrom`](../../client/lib/domain/dijkstra.dart)이 한 번만 돌려 전 노드
결과를 돌려주고, 목록은 매장의 `nodeId`로 조회만 한다. 갱신 시점도 검색어가
아니라 **위치**에 묶었다 — 검색을 시작할 때와 위치를 새로 잡았을 때만 계산한다.


**문제.** `search_panel.dart:759`의 `_storeTile`이 모든 항목에 같은
`Icons.place_outlined` 하나를 붙이고, subtitle은 층 문자열 단독이다. 목록만 보고
고를 수 없어 눌러봐야 안다. 이름은 통짜 볼드라 왜 이 결과가 나왔는지도 설명하지 않는다.

**제안.**

```
[핀]  죠죠 더현대서울점                     일식당
      B1 · 서관
      120m · 도보 2분
```

- title은 `Text.rich`로 쿼리 매칭 구간만 `AppColors.primary`
- trailing에 `subcategory` 회색 12px (좌측 아이콘은 지금대로 1종 유지)
- subtitle을 `층 · 구역`과 `거리 · 도보시간` 두 줄로

거리·도보시간은 PDR 앵커에서 `dijkstra`로 계산한다. **영업 상태·리뷰는 넣지 않는다**
(「벤치마크 경계」 참조).

**실패 조건.**

- 출발 위치가 없으면 거리를 계산할 수 없다. 그 경우 **거리 줄 자체를 생략**한다.
  `— m`이나 `거리 알 수 없음`을 넣으면 매 행마다 빈 값이 반복된다.
- `nodeId == null`인 매장은 경로 계산이 불가능하다. 지금은 subtitle에
  `경로 안내 불가`를 섞어 쓰는데(`search_panel.dart:767`), 거리 줄과 자리가 겹친다.
  네이버처럼 **필터로 분리**하거나 뱃지로 뺀다.
- 의미 검색 결과는 이름이 쿼리와 안 겹칠 수 있다. 하이라이트가 하나도 안 걸리는 경우가
  정상 상태다 — 그때 `_fromSemantic` 배너가 그 역할을 대신한다.

**검증 기준.**

- [ ] `나이키` 검색 시 이름의 `나이키` 구간만 파랑
- [ ] `밥 먹을 곳` 검색 시 하이라이트 없이 `_fromSemantic` 배너만 뜸
- [ ] 출발 위치가 없을 때 거리 줄이 사라지고 층 줄만 남음
- [ ] 소분류가 없는 매장에서 trailing이 대분류로 폴백
- [ ] 긴 매장명(`마리떼프랑소와저버/LMC`)에서 trailing 카테고리가 밀려나지 않음

### B. 상세 시트 액션 바를 하단 고정으로 <sub>시도 후 되돌림</sub>

**구현했다가 되돌렸다.** 스크롤 위치와 무관하게 길찾기에 닿는다는 이점보다, 두
자짜리 버튼 한 줄이 늘 시트 바닥을 차지하는 부담이 컸다. 폭을 반씩 나눠 채우는
안도 함께 시도했지만 버튼이 화면 절반씩 차지해 더 과했다.

출발·도착은 다시 **이름 바로 아래**, 본문 스크롤 안에 있다. `horizontal: 26,
vertical: 12` 그대로다. 같은 시도를 반복하지 않도록 근거를 `_PlaceActions`
주석에 남겼다.

**곁다리로 고친 것** — `_pop` 주석이 "길찾기 버튼은 하단 고정 바 한 곳에만 있다"고
적고 있었는데 구현은 처음부터 이름 아래였다. 주석을 구현에 맞췄다. 이 불일치가
애초에 B를 제안한 근거였는데, 실제로 화면에서 보니 구현 쪽이 맞았던 셈이다.

### C. 저장 버튼을 헤더로 이동 <sub>완료</sub>

B를 되돌린 뒤에도 C는 남는다. 저장은 **눌러도 시트가 그대로 남는 유일한 버튼**이라
시트를 닫는 출발·도착과 같은 줄에 있으면 무엇이 화면을 바꾸는지 예측이 안 된다.
네이버도 저장(☆)을 헤더 우상단에 둔다.

`SheetHeader`에 `trailing` 슬롯을 추가했다. 저장한 장소·카테고리 시트도 같은
헤더를 쓰므로 "pop을 일으키지 않는 위젯만" 이라는 계약을 주석에 박아 뒀다.

**여기서만 과거 결정을 뒤집었다.** 예전 주석은 "아이콘만으로 짐작하게 두지 않고
글자를 붙인다"였는데, 헤더는 자리가 아이콘 폭뿐이라 글자를 뗐다. 대신 채움/윤곽 +
tooltip + 스낵바 **셋으로** 그 자리를 메운다 — 셋 중 하나라도 빠지면 그냥 후퇴가
되므로 주석에 조건으로 적어 뒀다.

**문제.** 저장이 출발·도착과 같은 줄에 있다(`place_detail_sheet.dart:439`).
그런데 저장은 **누른 뒤 화면이 안 바뀌는 유일한 버튼**이다. 출발·도착은 시트를 닫고
경로로 넘어간다. 성격이 다른 것이 같은 줄에 있으면 무엇이 화면을 바꾸는지 예측이
안 된다.

**제안.** 네이버처럼 `SheetHeader`의 우측(`✕` 왼쪽)으로 옮긴다. 액션 줄은 행동만 담는다.
비는 자리에 `공유`를 넣을 수 있다.

**실패 조건.**

- 헤더는 `onCloseAll`/`onIntentionalPop` chain 계약을 들고 있다
  (`place_detail_sheet.dart:231`). 저장 버튼이 실수로 pop을 트리거하면 시트 chain이
  통째로 닫힌다. `_markIntentional`을 거치지 **않아야** 하는 유일한 버튼이다.
- `favorite == null`인 경우(placeId 없는 구 저장 항목) 지금은 버튼 자체를 감춘다.
  헤더로 옮기면 헤더 우측이 비므로 정렬이 흔들리지 않는지 본다.

**검증 기준.**

- [x] 저장을 눌러도 시트가 닫히지 않고 스낵바만 뜸
- [x] 저장 후 `저장됨` 상태가 유지된 채 출발·도착이 정상 동작
- [x] `favorite == null`인 장소에서 헤더 레이아웃이 깨지지 않음

### D. 접근 경로를 층 표기 아래에 추가 <sub>완료</sub>

**착수하며 실데이터를 먼저 확인했고, 그 결과 설계가 두 번 바뀌었다.**

**1. 화장실은 그래프 노드가 아니다.** 배포 그래프의 노드 타입은 `junction`(1720)·
`escalator`(152)·`elevator`(59) 셋뿐이다. 화장실은 **매장**으로 들어 있다
(`subcategory: '화장실'` + `entrance_node_id`, B2 기준 2곳). 그래서 노드 타입이
아니라 **층 도면의 매장 소분류**로 후보를 뽑는다.

**2. 기준점은 사용자가 아니라 그 매장이다.** 아래 원래 제안은 "현재 위치에서"를
전제했는데, 상세 시트에는 이미 바로 윗줄에 "나 → 매장" 거리가 있다. 같은 기준을
한 번 더 적으면 알려 주는 게 없다. 의미 있는 값은 **"이 매장에서 화장실이 얼마나
가까운가"**라 매장 입구 노드에서 [`reachableFrom`](../../client/lib/domain/dijkstra.dart)을
한 번 더 돌린다. 그래프는 이미 받아 둔 것을 재사용하므로 계산만 몇 ms다.

```
루이비통
1F · 명품
🚶 74m · 도보 2분      ← 나 → 매장 (A-2)
🚻 화장실 58m          ← 매장 → 시설 (D)
🛗 엘리베이터 55m
```

선택 로직은 [`nearby_facilities.dart`](../../client/lib/domain/nearby_facilities.dart)에
순수 함수로 두고 테스트로 덮었다.

**정한 실패 조건**

- **같은 층만 본다.** 다른 층 화장실을 "가장 가깝다"고 적으려면 층 이동까지 함께
  알려야 말이 된다. 이 층에 없으면 그 줄은 빠진다.
- 매장에 `entranceNodeId`가 없거나 그래프가 끊겨 도달 불가면 후보에서 버린다 —
  갈 수 없는 화장실을 가장 가깝다고 적지 않는다.
- 그래프·층 도면 로드 실패는 전부 빈 목록이다. 시설 안내는 부가 정보라 시트를 막지 않는다.
- 줄 순서는 화장실 → 엘리베이터 고정. 매장마다 순서가 바뀌면 눈이 매번 다시 찾는다.
- **에스컬레이터는 뺐다.** 152개라 거의 모든 매장이 "에스컬레이터 몇 m"가 되어
  정보가 되지 않는다.

아래는 착수 전 원안이다. 기준점 미결 상태로 남겨 뒀던 부분이 위에서 정해졌다.



**문제.** 네이버는 주소 바로 아래에 `⑤ 여의나루역 1번 출구에서 466m`를 둔다.
"어디인가" 다음이 "어떻게 닿는가"다. 우리 `_PlaceCore`는 `층 · 업종`에서 끝난다.

**제안.** 실내 앱에서는 이게 더 강력하다.

```
3F 서관 · 패션
🔼 에스컬레이터에서 20m · 도보 30초
```

가장 가까운 수직 이동 수단까지의 거리를 `floor_graph`에서 계산한다.

**실패 조건.**

- 수직 이동 노드가 같은 층에 없거나 그래프가 끊긴 매장이 있다. 그 경우 **줄을 생략**한다.
- 「가장 가까운 에스컬레이터」가 **사용자 진입 방향과 무관**하면 오히려 오해를 준다.
  주 출입구 기준인지 현재 위치 기준인지 먼저 정해야 한다. 정하지 않으면 착수하지 않는다.

**검증 기준.**

- [ ] 수직 이동 수단이 없는 층에서 줄이 생략됨
- [ ] 그래프가 끊긴 매장에서 예외 없이 생략됨
- [ ] 기준(주 출입구/현재 위치)이 문서에 명시돼 있음

### H. 지도 위 카테고리 필터의 위치 재고 <sub>설계 미확정</sub>

**관찰.** 네이버는 카테고리 필터를 **장소 상세 시트 안**에 둔다. 우리는 지도 위 상단
오버레이에 **상시** 띄운다(`map_shell_screen.dart:1089`).

**시트로 옮기면 얻는 것.**

- 상단 오버레이가 검색창 + 저장한 장소 pill 2단으로 줄어든다
- 실내에서만 노출하려는 `_mode == MapMode.indoor` 분기가 필요 없어진다
- 야외로 나갈 때 선택을 강제로 푸는 로직(`map_shell_screen.dart:235`)도 사라진다

**그러나 그대로 옮기면 깨진다.** 우리 pill은 누르면 **지도 위 매장이 파랗게 강조**되는데,
시트가 지도를 덮고 있으면 그 강조가 안 보인다. 네이버는 강조 대신 **시트 안 목록**으로
결과를 보여주기 때문에 이 문제가 없다.

**따라서 선택지는 둘이다.**

| 안 | 내용 | 대가 |
|---|---|---|
| 1 | pill을 누르면 시트가 접히고 지도 강조가 드러난다 | 시트 접힘 애니메이션·상태가 추가된다 |
| 2 | 지도 강조를 버리고 시트 안 목록으로 대체한다 | 「어느 자리에 있나」를 지도에서 못 본다 |

**우리 앱은 실내 지도가 핵심이라 2안은 손실이 크다.** 1안이 유력하지만 확정하지 않는다.
**착수 전에 팀에서 결정한다.**

**곁다리 — 필터 줄을 한 줄로 합치는 방법.** 우리는 대분류 줄과 소분류 줄을 세로로 쌓는다
(`map_shell_screen.dart:1067`, 주석에 이유가 적혀 있다 — 한 줄에 넣으면 소분류가 대분류
오른쪽 끝에 붙어 어디 딸린 것인지 안 읽힌다). 네이버는 성격이 다른 필터를 **세로 구분선**
하나로 나눠 한 줄에 둔다(`[N예약] │ [음식 130] [쇼핑 290] …`). 이 위치가 어디로 가든,
구분선 방식이면 두 줄을 한 줄로 줄일 수 있는지 검토할 여지가 있다. 다만 우리 두 줄은
**대분류-소분류 종속 관계**라 네이버의 병렬 관계와 다르므로, 그대로 적용되지는 않는다.

- 「인기 매장」은 **데이터가 없다.** 방문·클릭 로그가 없으므로 순위를 만들 수 없다.
  없는 걸 있는 척하면 안 된다 — 최근 검색어처럼 **클라이언트가 실제로 아는 것**부터 쓴다.
- 최근 검색어는 저장소가 필요하다. `favorites_controller`와 같은 계층에 둘지 정해야 한다.

**검증 기준.**

- [ ] 최근 검색어가 없는 첫 실행에서도 화면이 어색하지 않음
- [ ] 항목을 탭하면 그 검색어로 검색이 실행됨

# 야외 지도 화면 해체 (refactor/outdoor-map-decomposition)

`outdoor_map_screen.dart`의 `OutdoorMapBodyState` 하나를 완전히 해체하는 **장기 브랜치**의
계획서다. 이 브랜치는 기능을 추가하지 않는다. 동작이 한 줄이라도 달라지면 그건 실패다.

## 무엇을 해체하나

시작 시점(2026-08-14) 측정값이다.

| 항목 | 값 |
|---|---|
| 파일 | 8,569줄 |
| 메서드·게터 | 216개 (본문 8,134줄) |
| 상태 필드 | 156개 |

필드 156개는 성격이 뚜렷하게 갈린다 — **한 클래스에 상태 기계 7개가 얹혀 있다.**

| 상태 기계 | 필드 | 성격 |
|---|---|---|
| 실내 오버레이·층 | 49 | 진입 여부, 활성 층, 타일 소스 세대, 페이드 |
| 경로·안내 | 32 | 야외/실내/대중교통/보류 경로, 완료 이력, ETA |
| GPS·위치 | 16 | 구독, 최신 픽스, 정확도, 추적 |
| PDR·앵커 | 16 | 앵커, 배치 모드, 궤적, 보정 |
| 에스컬레이터·전환 | 13 | 탑승 판정, 활강, 전환 큐 |
| 지도·스타일·레이어 | 12 | 컨트롤러, 스타일 준비, 카메라 |
| 그 외 | 18 | 입구, 진행률, 리트라이 타이머 |

## 이 브랜치의 제1 제약 — rebase로 살아남기

이 브랜치는 오래 살고, 그동안 `main`에는 다른 PR이 계속 들어온다. **해체 방식보다 rebase
생존성이 먼저다.** 아래 다섯 개는 취향이 아니라 규칙이다.

1. **한 커밋 = 한 관심사.** 섞으면 충돌이 어느 작업의 것인지 알 수 없다.
2. **옮길 때 고치지 않는다.** 본문·주석을 글자 그대로 옮긴다. 이름 변경은 `_` 프라이버시
   때문에 불가피할 때만. 옮기면서 다듬으면 충돌 해결이 "어느 쪽이 맞는지 판단"이 되고,
   그 판단을 rebase마다 반복하게 된다.
3. **이동 대장(MOVES.md)을 남긴다.** `옛 심볼 → 새 파일:새 심볼`. rebase 충돌이 나면
   "이 함수 어디 갔지"를 찾는 데 드는 시간이 대부분인데, 대장이 있으면 기계적으로 끝난다.
4. **안 변하는 곳부터 뗀다.** 디버그·레이어 등록처럼 남이 잘 안 건드리는 코드가 먼저고,
   경로·에스컬레이터처럼 활발한 코드가 나중이다. 충돌 총량이 줄어든다.
5. **필드를 옮기는 커밋은 마지막에.** 필드 참조는 파일 전체에 흩어져 있어 충돌 면적이
   가장 넓다. 메서드를 다 뗀 뒤에 남은 필드를 옮긴다.

## 0단계 — 먼저 파일을 물리적으로 가른다

**한 번에 끝나고, 코드가 한 글자도 안 바뀐다.** 성격별 `part` 파일로 갈라 본체를
7,567 → 2,241줄로 줄인다.

| 파일 | 내용 |
|---|---|
| `outdoor_map_screen.dart` | 상수·위젯 클래스·**상태 필드 전부**·생명주기·build·공개 API 19개 |
| `outdoor_map_screen_route.dart` | 경로·안내·대중교통 |
| `outdoor_map_screen_indoor.dart` | 실내 오버레이·층·매장 |
| `outdoor_map_screen_pdr.dart` | PDR·앵커·보정 |
| `outdoor_map_screen_escalator.dart` | 에스컬레이터·층 전환 |
| `outdoor_map_screen_ui.dart` | 시트·배너·`_buildBody` |
| `outdoor_map_screen_map.dart` | 카메라·스타일·레이어 동기화 |
| `outdoor_map_screen_gps.dart` | GPS·위치 |

### mixin이 아니라 extension인 이유

둘 다 `part`로 파일을 가를 수 있지만 **mixin은 서로의 private 멤버를 못 본다.**
`mixin A on State<…>`은 `mixin B`가 선언한 `_foo`를 부를 수 없다. 멤버 335개가
서로 자유롭게 부르는 갓클래스에서는 어떤 경계로 갈라도 이 벽에 부딪힌다.

extension은 **같은 라이브러리 안에서 해석**되므로 private 멤버가 그대로 보이고
extension끼리도 서로 부른다. 대신 못 하는 것이 둘 있고, 둘 다 본체에 남겨 해결했다.

- **필드를 못 만든다** → 상태 필드 전부가 본체에 남는다(그래서 본체가 2,241줄이다).
- **`@override`가 안 된다** → `initState`·`dispose`·`build` 등 생명주기가 본체에 남는다.

`setState`는 `@protected`라 extension에서 부르면 분석기가 경고한다. 파일 단위로
이유를 적어 껐다 — 남의 protected 멤버가 아니라 **같은 클래스의 코드**가 파일만
갈라져 있는 것이기 때문이다.

### 이것이 사는 것과 사지 못하는 것

**산다.** 읽어야 하는 파일이 1/3로 줄고, `main`의 변경이 해당 part 하나에만 떨어져
rebase 충돌 면적이 준다. 그리고 각 part가 "진짜 클래스로 승격할 후보"로 눈에 보인다.

**못 산다.** 결합은 그대로다. 여전히 한 클래스에 필드 150개고 아무나 아무거나
만질 수 있다. **이건 가독성 단계이지 분리 단계가 아니다.** 진짜 분리는 아래
1~7단계가 계속 한다.

### 왜 이 방식이 안전한가

멤버 텍스트를 글자 그대로 옮기고, **분할 전후의 코드 토큰이 같은지 기계로 대조**했다.
차이는 part 파일 7개의 extension 닫는 괄호 7개뿐이었다(29,214 → 29,221 토큰).
동작이 달라질 여지가 구조적으로 없다.

## 순서

각 단계는 앞 단계가 끝나야 시작할 수 있다(의존 방향이 그렇다).

| # | 단계 | 대상 | 예상 | 상태 |
|---|---|---|---|---|
| 1 | 레이어 쓰기 모듈화 | 위치·목적지·강조·스크림·건물·외곽선 sync | ~740줄 | **완료** |
| 2 | 카메라 명령 분리 | fit·animate·recenter | ~660줄 | **완료** |
| 3 | GPS 세션 추출 | 필드 16 + 메서드 | ~460줄 | **완료** |
| 4 | PDR 세션 수명 추출 | 필드 1 + 메서드 3 | ~25줄 | **완료** |
| 5 | 실내 오버레이 세션 추출 | 필드 49 + 타일 등록 + **지도 탭 판정** + **PDR 앵커 상태** | ~1,530줄 | **진행 중** |
| 6 | 경로 표시 상태 추출 | 필드 32 + 표시 판단 | ~940줄 | |
| 7 | build 분해 | 오버레이 위젯들 | ~780줄 | |

1~2는 상태를 옮기지 않았다(호출부가 데이터를 넘긴다). 3부터가 진짜 해체다.

### 남은 줄이 어디 있는지 실제로 재 봤다

4단계까지 끝낸 시점(7,915줄)에 클래스 멤버를 성격별로 재니 이렇다.

| 성격 | 줄 | 멤버 |
|---|---|---|
| 실내 오버레이·층·타일 | 2,786 | 103 |
| **어느 단계에도 없던 것** | 1,123 | 86 |
| 경로·안내 | 953 | 59 |
| build·위젯 | 819 | 24 |
| GPS·위치(3단계에서 일부만) | 386 | 16 |
| PDR·앵커 | 363 | 26 |
| 에스컬레이터(손대지 않음) | 317 | 24 |

여기서 두 가지가 드러났다.

1. **1~4단계는 전부 주변부였다.** 뗀 1,277줄이 레이어 쓰기·카메라·GPS·세션
   수명이고, 41%를 차지하는 실내 오버레이는 손도 안 댔다.
2. **위 단계 표의 합(5·6·7 = 약 3,250줄)으로는 목표에 못 간다.** 7,915에서
   빼도 4,665줄이 남는다. "어느 단계에도 없던 1,123줄"(입구 처리, 카테고리 필터,
   스타일 등록, 탭 라우팅, 생명주기)을 계획이 아예 세지 않았기 때문이다.

그래서 목표를 다시 적는다. **에스컬레이터(317)와 조립·생명주기·공개 API를 빼고
나머지를 전부 옮기면 1,200~1,500줄**이 남는다. 그 이하는 이 브랜치에서 손대지
않기로 한 코드 때문에 불가능하다.

### 5단계를 현장 검증 전에 시작한 이유

원래는 "현장 검증 후"로 미뤄 두었다. 그 판단에 결함이 있었다.

**월요일 현장 검증은 `claude/msa-...-2` 브랜치 APK로 한다.** 즉 그 검증은 5단계를
검증하지 않는다 — 기준선만 잡는다. 기다려도 5단계의 검증 부채는 그대로 남고
현장에 또 나가야 한다. 3일을 대가로 사는 것이 없다.

대신 폰으로 **실내 오버레이가 실제로 그려지는 것을 원격으로 확인할 수 있다는 것**을
알았다(길찾기를 열면 카메라가 더현대로 가고 도면·매장 폴리곤·라벨이 뜬다). 그리고
스타일 로드마다 찍히는 로그가 등록 성공을 매번 알려 준다.

```
[outdoor overlay] registering MVT source url=.../floors/1F/tiles/{z}/{x}/{y}.mvt
[outdoor overlay] MVT source+layers registered (1F)
```

**단계마다 APK를 폰에 올려 이 두 줄과 도면 화면을 확인한다.**

### 도면 화면을 책상에서 띄우는 법 — `starbucks`

카메라를 더현대로 보내려면 매장을 검색해야 하는데 `adb shell input text`는 한글을
못 보낸다(ASCII만 간다). 그런데 **검색이 로마자를 한글로 맞춰 준다**
([검색 입력 보조](search-input-assist.md)). 그래서 이렇게 하면 된다.

```powershell
$adb = "C:\Users\HANSUNG\AppData\Local\Android\Sdk\platform-tools\adb.exe"
& $adb shell input tap 770 223       # 상단 검색창
& $adb shell input text "starbucks"  # → "스타벅스 리저브 · 더현대 서울 · B2"가 1위
& $adb shell input tap 400 500       # 첫 결과
& $adb shell screencap -p /sdcard/s.png
& $adb pull /sdcard/s.png .
```

첫 결과를 누르면 카메라가 **B2로 층까지 전환**되며 실내 오버레이가 뜬다. 즉 이 한
번으로 등록·층 전환(세대 증가)·강조·라벨·아이콘이 한꺼번에 눈에 걸린다.

화면에서 확인할 것: 매장 폴리곤이 **검지 않은지**, 매장명 라벨과 대분류 아이콘이
살아 있는지, 고른 매장이 파랗게 강조되는지. 셋 중 하나라도 어긋나면 속성 전체 교체
규칙(이 문서 맨 위 파일 주석)을 깬 것이다.

그 밖에 이 단계의 근거는 둘 더 있다.

- 등록 성공 로그(위 두 줄) — 등록이 예외로 실패하면 안 찍힌다.
- `test/screens/outdoor_map/indoor_overlay_layers_test.dart` — 도면이 검게 뜨는 그 사고를 직접
  막는 테스트다(모든 fill의 `fill-color`가 null이 아님, symbol의 layout 속성 생존).

**그래서 실내 *렌더링*은 현장에 나가지 않아도 검증된다.** 현장이 필요한 것은 GPS
판정·PDR·에스컬레이터처럼 **거기 서 있어야만 참/거짓이 갈리는 것**뿐이다
([현장 검증 체크리스트](field-verification-thehyundai.md)).

### 지도 탭 판정을 3단계에서 뺀 이유

원래 계획은 탭 판정(탭 → 매장 확정, ~470줄)을 상태 이동 전에 떼는 것이었다. 실제로 열어
보니 **뗄 수 있는 모양이 아니었다.**

- 매장을 고르는 데 쓰는 레이어 id가 `late String _indoorStoresLabelLayerId = _idFor(...)`
  처럼 **세대(generation)가 붙은 인스턴스 필드**다. 실내 오버레이 세션이 소유할 상태이고,
  그것보다 먼저 떼면 id 세 개를 인자로 계속 끌고 다니는 함수가 된다.
- 한 폴리곤을 여럿이 나눠 쓸 때 목록 시트를 띄워 사용자에게 되묻는다
  (`showStoreClusterSheet`). 즉 이 코드는 "무엇이 손가락 밑에 있나"와 "누구를 고를지
  사용자에게 묻는다"가 붙어 있다. 후자는 UI라 7단계(build 분해)의 몫이다.

그래서 탭 판정은 **5단계(실내 오버레이 세션)와 함께** 옮긴다. 규칙 4("안 변하는 곳부터")와
규칙 5("필드 이동은 마지막")를 지키려다 오히려 인자만 늘어나는 함수를 만들 뻔했다.

### 4단계가 계획(필드 16)보다 훨씬 작아진 이유

원래 4단계는 "PDR 앵커 세션"(필드 16, ~360줄)이었다. 열어 보니 그 16개는 **하나의 상태
기계가 아니라 두 개**였고, 둘의 성격이 정반대였다.

- **세션 수명** — 언제 켜고 끄는가. 화면 없이 참/거짓이 갈린다. 이번에 뗐다.
- **앵커 배치** — 어디에 찍을 것인가. 스낵바(`_showSnack`), 방향 보정 다이얼로그
  (`_askScreenDirection`), 지도 탭, 카메라 bearing이 한 흐름에 엮여 있다.

뒤엣것을 지금 떼면 콜백을 넷 이상 주입해야 하고, 그래도 남는 것은 "화면을 인자로 받는
클래스"다. 게다가 그 코드는 **책상에서 참/거짓이 갈리지 않는다** — 실내 앵커라 현장에서만
확인된다. 그래서 앵커 상태는 UI 조각들이 함께 움직이는 5단계로 넘겼다.

3단계의 지도 탭 판정과 같은 판단이다: 계획의 묶음이 실제 코드의 이음매와 다르면 **코드
쪽을 따른다.** 억지로 묶으면 인자만 늘어난 함수가 남고, 그 함수는 rebase마다 충돌한다.

### 이번 단계에서 배운 것 — 이 경합은 위젯 테스트로 못 잡는다

4단계의 핵심은 "아직 끝나지 않은 정지를 시작이 기다리는가"다. 이걸 3단계처럼 위젯
특성 테스트로 먼저 고정하려다 **무력한 테스트**를 만들었다 — `awaitStop`을 통째로 빼도
통과했다.

원인은 둘이다.

1. 모의 MethodChannel 핸들러 안의 `Future.delayed`는 `tester.pump`가 앞당길 수 있는
   가짜 시계가 아니라 **실제 시계**를 쓴다. 그래서 "정지가 도는 중"인 창을 원하는
   길이로 만들 수 없다.
2. 창을 못 만드니 단언이 `isNot(idle)`로 느슨해졌는데, 실패 상태인 `stopping`도
   `idle`이 아니라서 **틀린 코드에서도 참**이었다.

그래서 위젯 테스트를 버리고 [PdrSessionLifecycle]을 **직접** 시험했다
(`test/screens/outdoor_map/pdr_session_lifecycle_test.dart`). 거기서는 정지 Future를 테스트가
쥐고 있어 창을 원하는 만큼 열어 둘 수 있다 — 세션 수명을 화면에서 떼어낸 값어치가
바로 이것이다.

다음 단계에 적용할 규칙: **특성 테스트를 쓰기 전에 "이 테스트가 틀린 코드에서 실패하는지"를
먼저 확인한다.** 통과하는 것만 보고 넘어가면 아무것도 지키지 못하는 테스트가 남는다.

## 검증 게이트

단계마다 아래를 전부 통과해야 다음으로 넘어간다. 하나라도 빨간불이면 그 단계는 되돌린다.

- `flutter analyze` 0건
- `flutter test test/` 전부 통과
- 공개 API 19개의 이름·시그니처 불변 (`grep`으로 확인)
- **동작 동일성의 근거를 커밋 메시지에 적는다.** "옮기기만 했다"면 그렇게, 로직이 한 줄이라도
  바뀌었으면 무엇이 왜 바뀌었는지.

### 데스크에서 증명할 수 없는 것

실내 도면 렌더링·PDR·층 전환은 책상에서 참/거짓이 갈리지 않는다
([현장 검증 체크리스트](field-verification-thehyundai.md)의 앞부분 참고). 그래서 이 브랜치는
**현장 검증을 통과하기 전까지 병합하지 않는다.** 단계 6(실내 오버레이)은 그중에서도 가장
위험해 — 실기기에서 도면이 통째로 검게 뜬 이력이 있는 코드다 — 현장 기준선을 잡은 뒤에
착수한다.

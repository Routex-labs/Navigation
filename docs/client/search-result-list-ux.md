# 검색 결과 목록 UX — 후보 목록과 결과 목록이 갈라진 자리

네이버지도·카카오맵의 **검색 결과 화면**을 다시 보고, 우리 `SearchPanel`이 그 자리에서
무엇을 덜 하고 있는지 정리한다.

- [네이버지도 UI/UX 분석](naver-map-ui-ux-analysis.md)이 **정보 구조와 목록·시트 UX**
  (A~J), [검색 입력 보조](search-input-assist.md)가 **매칭 품질과 입력 보조**(K~N)를
  다룬다. 이 문서는 그 둘이 만나는 자리 — **입력이 끝난 뒤 사용자가 실제로 고르는
  목록** — 을 다루고, 항목 번호는 겹치지 않게 **O부터** 이어 붙인다.
- 매칭 파이프라인 자체(임계값·인덱스 문서·facet)는 손대지 않는다. 단일 출처는
  [query.md](../backend/native/query.md) · [FAISS.md](../backend/native/FAISS.md) ·
  [conversational-discovery.md](../backend/native/conversational-discovery.md)다.
- 정상 동작보다 **실패 조건을 먼저** 적고, **무엇이 충족되면 맞다고 볼지**를 함께 적는다
  (AGENTS.md 규칙).

## 이번 회차 벤치마크의 한계 — 먼저 적는다

[naver-map-ui-ux-analysis.md](naver-map-ui-ux-analysis.md)의 A~J는 사람이 직접 조작해
캡처한 6개 화면이 근거였다. **이번 회차에는 새 캡처가 없다.** 네이버 도메인이 계정
안전 정책으로 여전히 에이전트에게 차단돼 있고, 카카오맵도 모바일 앱 화면은 같은
방식(사람이 조작·캡처)이 아니면 확보할 수 없다.

그래서 이번 근거는 셋으로 나뉜다. **어느 문장이 어디에 기대고 있는지 구분해서 읽어야
한다.**

| 근거 | 성격 | 신뢰도 |
|---|---|---|
| 기존 캡처 6장(2026-08-03, 네이버 데스크톱 웹) | 1차 관찰 | 높음 — 다만 데스크톱 |
| 공개 UX 분석 글·카카오 공식 개편 공지 | 2차 자료 | 중간 — 시점·버전이 우리와 다를 수 있다 |
| **우리 코드와 시드 데이터 실측** | 1차 | 높음 — 아래 수치는 전부 이쪽이다 |

**따라서 이 문서의 결론은 "네이버가 이러니까 하자"가 아니라 "우리 화면에 이런 구멍이
있고, 두 앱은 그 자리를 이렇게 메운다"의 순서로 쓴다.** 벤치마크가 근거의 전부인
항목은 그렇다고 표시했다.

## 관찰 — 우리 검색 화면에는 목록이 **두 벌** 있다

`search_panel.dart`를 읽으면 사용자가 보는 목록 화면이 실제로는 두 개다.

| | `_suggestionList()` | `_resultList()` |
|---|---|---|
| 언제 | 타이핑 중 · 서버가 `ambiguous`/`no_match`일 때 | 서버가 1건 확정 · 의미 검색 결과 |
| 원본 | 온디바이스 `store-index` | `/query/destination` · `/query/ai` |
| 이름 강조 | ✅ | ✅ |
| 업종 | ✅ | ✅ |
| 층 | ✅ | ✅ |
| **거리 · 도보 시간** | ❌ **없음** | ✅ `reachLabel` |
| **거리순 정렬** | ❌ 매칭 품질순 | ✅ `sortedByWalkingDistance` |
| 추천 이유 | — | ✅ |
| 탭했을 때 | 그 이름으로 **재검색** | 매장으로 **바로 이동** |

**A-2(거리 표시)와 M(거리순 정렬)은 오른쪽 목록에만 들어갔다.** 왼쪽 목록은 K에서
새로 만들면서 "자동완성은 입력 보조"라는 전제로 이름·층만 그렸다.

### 문제 — 왼쪽 목록은 입력 보조가 아니라 **결과 화면**으로도 쓰인다

`_search()`가 서버 결과를 받은 뒤 이 분기를 탄다.

```dart
if (results.isEmpty && building == null) {
  if (_suggestions.any((s) => !s.kind.isCorrection)) {
    ... _phase = _SearchPhase.suggestions;   // 여기서 끝. 의미 검색으로 안 넘어간다
    return;
  }
```

즉 **서버가 한 곳을 지목하지 못한 질의는 후보 목록이 최종 화면이 된다.** 그리고 서버가
지목하지 못하는 조건은 예외가 아니라 규칙이다 — `match_destination`은 최상위 그룹에
서로 다른 매장명이 둘 이상이면 `status="ambiguous"`로 비워 보낸다
(`query_search.py:372`). 브랜드 이름은 대부분 여기 걸린다.

#### 실측 — 얼마나 자주 걸리나 (시드 1640건, 서로 다른 이름 655건)

이름 앞 N글자를 질의로 넣었을 때, 접두로 걸리는 **서로 다른 이름**이 2건 이상인 비율:

| 질의 길이 | 후보 2건 이상 |
|---|---|
| 앞 2글자 | 152/652 = **23%** |
| 앞 3글자 | 70/510 = **14%** |
| 앞 4글자 | 42/382 = **11%** |
| 첫 단어 통째로 | 50/602 = **8%** |

**그리고 걸리는 쪽이 하필 이 건물의 간판이다.**

```
디올    → 디올 뷰티(1F) · 크리스챤 디올 (남/여)(1F) · 디올 선글라스(2F)
나이키  → 나이키 골프(4F) · 나이키스윔(4F) · 나이키 라이즈(B2)
메종    → 5건, 1F~3F에 흩어져 있음
```

명품·스포츠 브랜드는 **뷰티/선글라스/남성관을 층을 갈라 낸다.** 사용자가 브랜드명을
치는 흔한 이유가 바로 "어느 층으로 가야 하나"인데, 정작 그 질의가 **거리도 정렬도 없는
목록**으로 간다. 8%라는 숫자가 작아 보여도, 그 8%가 사용자가 이름을 알고 찾아오는
목적형 검색의 대부분이다.

> **주의 — 위 수치는 온디바이스 후보 수이지 서버의 `ambiguous` 조건이 아니다.**
> 서버는 **최상위 tier 그룹**에 서로 다른 이름이 둘 이상일 때만 `ambiguous`를 준다.
> 그래서 `구찌`·`프라다`처럼 **그 이름 그대로인 매장이 실재하면** tier 0 정확 일치가
> 단독 1위가 되어 서버는 자신 있게 1건을 확정한다. 이 경우는 후보 목록이 아니라
> **결과 1행**으로 끝난다 — 그리고 그게 아래 S가 지적하는 별개의 문제다.

### 더 나쁜 자리 — 묶인 시설의 대표가 **사용자와 무관하게** 정해진다

`suggestStores()`는 같은 이름을 하나로 묶고 개수만 `duplicateCount`에 담는다. 화면은
`'${store.floorName} 등 ${duplicateCount}곳'`을 찍는다(`search_panel.dart:780`).

**대표로 남는 매장은 "인덱스에서 처음 나온 것"이다.** 그리고 인덱스 순서는
`Floor.level DESC, Store.id`로 서버가 못박아 뒀다(`building_queries.py:141`). 즉 —

```
사용자가 B2에 서 있어도:   화장실 · 6F 등 19곳
```

**항상 꼭대기 층이 대표다.** 화장실 19곳은 1F~B3에 흩어져 있는데, 화면은 그중 가장 먼
축에 드는 곳의 층을 적는다. 이건 정보가 없는 게 아니라 **틀린 정보다** — 사용자는
`6F`를 "여기서 가까운 화장실이 6층"으로 읽는다.

정수기 14곳·엘리베이터 60곳·에스컬레이터 152곳이 전부 같은 경로다.

> **이건 K절이 예고하지 못한 실패 조건이다.** K는 "같은 이름이 12건씩 나오니 묶는다"
> 까지만 정했고, **묶은 뒤 무엇을 대표로 세울지**는 정하지 않았다. 그래서 구현이
> "처음 나온 것"이라는 임의값을 골랐고, 그 임의값이 하필 층 정렬 때문에 최악에
> 가까웠다.

## 벤치마크 — 두 앱은 이 자리를 어떻게 쓰나

### 네이버 (기존 캡처 · 1차 관찰)

- **자동완성과 결과 목록의 행이 다르다.** 자동완성은 돋보기/핀 2종 아이콘 + 이름 +
  회색 카테고리 + 주소 2행이고, 결과 목록은 거기에 **볼드 거리** + 썸네일 +
  `출발|도착` 버튼이 붙는다(「3. 검색 결과 목록」).
- **거리가 볼드다.** 목록에서 가장 강한 판단 기준으로 취급한다.
- **정렬·필터를 칩으로 늘어놓지 않는다.** 섹션 헤더 우측에 `추천순 ⌄`처럼 **텍스트 +
  chevron**으로 접는다(「1. 지도 홈」).
- 내부시설 목록에 **개수를 pill 안에 넣는다** — `내부시설 497`, `음식 130`.

### 카카오 (2차 자료)

- 2023년 장소상세 개편의 방향이 "필수 정보(예약·길찾기·즐겨찾기)를 첫 화면에서 바로
  누르게" 였다. 목록·상세에서 **다음 행동까지의 탭 수를 줄이는 것**이 일관된 축이다.
- 지하철 출구 검색이 강하다는 점은 이미 K절 「벤치마크 경계」에 적혀 있다.

### 공통 원칙 (NN/g)

- 검색 제안은 **관련성 없는 항목을 절대 섞지 말 것** — 제안이 무관한 결과를 내면
  사용자는 검색 자체를 불신한다.
- 모바일에서는 제안을 **텍스트로 단순화**한다. 우리가 후보 행에 썸네일 같은 걸 넣을
  이유는 없다는 뜻이기도 하다.

### 벤치마크 경계 — 가져오지 않을 것

| 요소 | 우리 |
|---|---|
| 썸네일 사진 | ✗ 데이터 없음. 넣을 자리를 비워 두지도 않는다 |
| 리뷰 수·평점·영업시간 | ✗ `store_details/_schema.json`의 `forbidden_labels`가 코드로 막는다 |
| 「추천순」 | ✗ 방문·클릭 로그가 없어 순위를 만들 근거가 없다(J절과 같은 이유) |
| 직선거리 「가까운 순」 | **우리는 보행 거리로 한다** — 실외 지도가 흉내낼 수 없는 자리(M절) |

## O. 후보 목록에도 거리를 붙이고, 묶인 시설은 **가장 가까운 곳**을 대표로 세운다

### 문제

위 두 절이 그대로 문제다. 요약하면 —

1. 브랜드 검색(23%/2글자 기준)은 후보 목록이 최종 화면인데 거리가 없다.
2. 묶인 시설(화장실·정수기·엘리베이터)의 대표 층이 **꼭대기 층으로 고정**돼 있다.

### 제안

**추가 통신도, 추가 계산도 없다.** 필요한 두 가지가 이미 다 있다.

- `StoreIndexEntry.entranceNodeId` — `store-index` 응답에 이미 들어 있다.
- `SearchPanel.reachByNodeId` — 상위가 위치를 잡을 때 `reachableFrom`을 **한 번** 돌려
  전 노드 결과를 내려준다. 조회만 하면 된다(M절과 같은 근거).

```
[돋보기]  화장실                       화장실
          B2 등 19곳                   ← 6F가 아니라 지금 가장 가까운 층
          48m · 도보 1분               ← 그 대표까지의 보행 거리

[돋보기]  구찌 뷰티                    화장품
          1F
          120m · 도보 2분
```

그룹 대표를 고르는 규칙은 **순수 함수 하나**로 두고 테스트로 덮는다. `suggestStores()`
안에 넣지 않는다 — 그쪽은 라우팅을 모르는 매칭 전용 함수이고, 거리를 알려면 화면
상태(`reachByNodeId`)가 필요하다. 섞으면 매칭 로직이 위치 유무에 따라 달라진다.

### 순서는 **건드리지 않는다** (중요)

거리 라벨만 붙이고 **정렬은 매칭 품질순 그대로 둔다.** 세 가지 이유다.

1. **후보 목록은 타이핑 중에도 같은 위젯이다.** 타이핑 중에 거리로 세우면 글자를 칠
   때마다 목록이 위아래로 튄다. 사용자는 아직 무엇을 찾는지 확정하지 않았고, 그 단계의
   올바른 순서는 "얼마나 잘 맞는가"다. 네이버 자동완성도 매칭순이다.
2. **M이 정한 규칙과 충돌하지 않는다.** M은 "의미가 다른 두 순서를 섞지 않는다"였다.
   매칭 품질순과 거리순도 의미가 다른 두 순서다.
3. 정렬을 **고르게** 하는 것이 옳은 해법이고, 그건 아래 P다. O에서 몰래 바꾸지 않는다.

**단, 그룹 대표 선택은 정렬이 아니라 「19곳 중 어느 하나를 화면에 적을 것인가」다.**
지금도 임의로 하나를 고르고 있으므로, 그 임의값을 "가장 가까운 곳"으로 바꾸는 것은
순서 변경이 아니다.

### 실패 조건 (먼저 정한 것)

- **위치가 없을 때.** `reachByNodeId`가 null이거나 비어 있다(PDR 미시작·측위 실패).
  → **거리 줄을 그리지 않고, 대표도 지금과 똑같이 인덱스 첫 번째를 쓴다.** 결과 목록이
  같은 상황에서 거리 줄을 통째로 생략하는 것과 같은 규칙이다(A절 실패 조건).
- **그룹 일부만 도달 가능.** 화장실 19곳 중 3곳만 `reachByNodeId`에 있을 수 있다(그래프
  단절·`entranceNodeId == null`). → **도달 가능한 것 중 최근접**을 대표로 쓴다.
  `duplicateCount`는 **줄이지 않는다** — 19곳이 있는 건 사실이고, 우리가 거리를 아는
  게 3곳일 뿐이다. 개수를 3으로 줄이면 없는 사실을 만들어 낸다.
- **전원 도달 불가.** → 지금 동작 유지(첫 번째 대표, 거리 줄 없음).
- **대표가 바뀌면 층 라벨도 바뀐다.** 이건 부작용이 아니라 목적이다. 다만 `store.id`가
  바뀌므로 `ListTile`의 `Key('suggestion-${store.id}')`도 함께 바뀐다 — 위치를 새로
  잡을 때 그 행이 재생성되는지, 스크롤·탭 판정이 흔들리지 않는지 확인한다.
- **탭했을 때 무엇으로 재검색하나.** 후보 탭은 `onQueryPicked(store.name)`으로 **이름**을
  넘긴다. 그룹은 *정규화한* 이름으로 묶으므로 대체로 원문도 같지만, `물품 보관함`과
  `물품보관함`처럼 **표기만 다른 이름이 한 그룹에 들어오면 대표가 바뀔 때 넘기는
  문자열도 바뀐다.** 둘 다 실재하는 상호라 서버가 어느 쪽으로도 찾아내므로 손실은
  없고, 오히려 화면에 적힌 이름과 재검색어가 일치한다는 점에서 지금보다 정확하다.
- **탭한 뒤의 목적지는 여전히 서버가 정한다.** 대표 층을 B2로 고쳐도 재검색은 이름만
  넘기므로 서버가 다른 층을 확정할 수 있다. **O의 범위 밖이고**, 아래 「남은 문제」다.
- **결정성.** 거리가 완전히 같은 두 매장(같은 노드를 공유)이 있으면 매번 같은 쪽이
  뽑혀야 한다. → 동점은 **인덱스 순서**로 깬다. `List.sort`가 안정 정렬이 아니라는
  M절의 교훈을 그대로 적용한다.
- **성능.** 후보 8건 × 그룹 최대 152건(에스컬레이터) = 최악 1216회 맵 조회다. 해시맵
  조회라 무시할 수 있지만, 그러려면 **그룹 구성원을 후보마다 다시 훑지 않아야** 한다.
  `suggestStores()`가 이미 만든 그룹을 그대로 넘긴다.

### 검증 기준 (착수 전에 정한 것)

전부 자동 테스트로 덮었다 — 순수 함수는
[`nearest_store_test.dart`](../../client/test/domain/nearest_store_test.dart), 화면 배선은
[`search_panel_test.dart`](../../client/test/widgets/search_panel_test.dart)의
「후보 목록의 거리와 대표 층」 그룹이다.

- [x] 위치가 있을 때 후보 행에 `Nm · 도보 N분`이 뜬다 — 묶인 시설·단일 매장 양쪽
- [x] 위치가 없을 때 후보 행이 **지금과 완전히 같다** (대표는 인덱스 첫 번째, 거리 줄 없음)
- [x] `화장실`의 대표 층이 인덱스 첫 번째(6F)가 아니라 최근접(B2)이다
- [x] 그룹 중 일부만 도달 가능해도 `등 N곳`의 **N이 그대로다**
- [x] 전원 도달 불가인 그룹에서 예외 없이 지금 동작으로 떨어진다
- [x] 거리 동점 40건에서 대표가 매 호출 동일하다 (M절과 같은 규모 — 2~3건은 삽입 정렬
      경로라 우연히 통과한다)
- [x] 후보 **순서**가 거리 도입 전후로 동일하다 — `타임`(가까움 300m) / `타임옴므`(10m)
      에서 여전히 짧은 이름이 1위다. O가 정렬을 안 바꾼다는 것을 테스트로 못박았다.

#### 구현하며 함께 정한 것 — 개수 필드를 지웠다

`StoreSuggestion`이 들고 있던 `duplicateCount`를 없애고 **묶인 매장 목록 자체**
(`stores`)를 넘기도록 바꿨다. 대표를 화면에서 고르려면 목록이 필요한데, 목록과 개수를
둘 다 두면 같은 사실을 두 곳에 적는 셈이라 한쪽이 먼저 썩는다. 개수는 이제
`stores.length`다.

**대표 선택을 `suggestStores()` 안에 넣지 않았다.** 그쪽은 라우팅을 모르는 매칭 전용
순수 함수인데, 거리를 알려면 화면 상태(`reachByNodeId`)가 필요하다. 섞으면 매칭 결과가
위치 유무에 따라 달라진다 — 지금은 위치가 있든 없든 **후보와 그 순서가 동일**하고,
달라지는 건 한 줄 안에서 어느 매장을 대표로 적느냐뿐이다.

## P. 정렬 기준을 화면에 드러내고 고를 수 있게 한다

### 문제

**지금 결과 목록은 조용히 거리순으로 세워진다.** 화면 어디에도 그렇다는 말이 없다.
그리고 세우지 **않는** 조건이 셋이나 된다(의미 검색 결과 / 위치 없음 / 거리를 모르는
매장). 사용자는 목록을 보고 그중 어느 상태인지 알 방법이 없다.

같은 화면이 상황에 따라 다른 순서를 쓰는데 그 사실이 화면에 없으면, 사용자는 **위쪽이
무엇을 뜻하는지** 알 수 없다. M절이 "두 순서는 의미가 다르다"고 정확히 지적해 놓고,
정작 그 의미를 화면에 적지 않았다.

### 제안

네이버처럼 **텍스트 + chevron**으로 목록 머리에 둔다. 칩 줄을 새로 늘리지 않는다.

```
검색 결과 3                     가까운 순 ⌄
─────────────────────────────────────────
```

- 선택지는 **`가까운 순` · `이름 맞춤 순`** 둘뿐이다. 「추천순」은 만들지 않는다 —
  근거가 될 로그가 없다(위 「벤치마크 경계」).
- **위치가 없으면 `가까운 순`을 고를 수 없다.** 비활성으로 두고 이유를 적는다.
  ("현재 위치를 잡으면 가까운 순으로 볼 수 있어요")
- 의미 검색 결과에서는 정렬 컨트롤 자체를 **띄우지 않는다.** 유사도순은 사용자가
  고를 수 있는 축이 아니다.

### 실패 조건 (먼저 정한 것)

- **결과가 1건일 때 컨트롤이 뜨면** 누를 이유가 없는 버튼이 된다. → 2건 이상에서만.
- **후보 목록과 결과 목록에 같은 컨트롤을 두면**, 후보 목록에서 정렬을 바꾼 뒤 서버
  응답이 도착해 결과 목록으로 넘어갈 때 선택이 유지돼야 한다. 유지 안 되면 사용자가
  방금 한 조작이 사라진다.
- **선택을 세션 간 저장할지.** 저장하면 다음 검색이 갑자기 다른 순서로 시작하고,
  저장 안 하면 매번 다시 골라야 한다. → **기본 제안: 저장하지 않고 매 검색 `가까운 순`
  으로 시작.** 위치를 모르면 `이름 맞춤 순`으로 시작.
- **P는 O에 의존한다.** 후보 목록에 거리가 없는 상태에서 `가까운 순`을 고르게 하면
  정렬 기준이 화면에 안 보이는 목록이 된다.

### 검증 기준

- [x] 결과 2건 이상일 때만 컨트롤이 뜬다 (`canChooseSortOrder`)
- [x] 위치가 없을 때 `가까운 순`이 비활성이고 이유가 적혀 있다
      (`가까운 순 (현재 위치 필요)`)
- [x] 의미 검색 결과에서 컨트롤이 안 뜬다
- [x] 후보 목록 → 결과 목록으로 넘어갈 때 선택이 유지된다 — 초기화 시점을
      `_search` 호출이 아니라 **검색어 변경**에 묶었다. 같은 검색어로 다시 엔터를
      눌러도 선택이 남는다.
- [x] `이름 맞춤 순`이 K절의 매칭 품질 순서와 **정확히 같다** — `bestMatch`는
      정렬 함수가 입력을 **사본조차 만들지 않고** 그대로 돌려주므로 순서 규칙이
      두 벌이 될 수 없다(`identical()`로 테스트).
- [x] 타이핑 중에는 컨트롤도 거리 정렬도 없다 — 아직 결론이 아닌 화면이 결론처럼
      보이면 안 되고, 글자마다 줄이 위아래로 튀면 고를 수가 없다.
- [x] 오타 교정 화면에는 뜨지 않는다 — 교정은 추측이라 개수를 세고 거리로 세워
      주는 것 자체가 "이게 답이다"라는 말이 된다.

#### 구현하며 정한 것 — 「조용한 정렬」이 두 곳에 있었다

문서를 쓸 때는 결과 목록만 봤는데, 실제로 정렬이 사용자에게 가장 크게 작용하는
자리는 **후보 목록**이었다(위 「관찰」의 브랜드 질의). 그래서 정렬 컨트롤도 두
목록에 함께 붙였고, 후보용 `sortedSuggestions()`를 따로 뒀다.

**후보의 정렬 기준은 화면에 적히는 거리와 같은 값이어야 한다.** 후보 한 줄이
여러 매장일 때(화장실 19곳) 대표(최근접)의 거리로 세우지 않으면, **화면의 숫자가
오름차순이 아닌 목록**이 나온다. O의 대표 선택과 P의 정렬이 같은 값을 봐야 하는
이유다.

## Q. 결과 개수와 층 분포를 머리말에 적는다

### 문제

지금 목록에는 머리말이 없다. `검색어 제안`·`최근 검색어`는 있는데, 결과 목록만 바로
행부터 시작한다. 그래서 **몇 건인지, 몇 개 층에 걸쳐 있는지** 스크롤해 보기 전에는
모른다.

네이버는 `내부시설 497`처럼 개수를 pill 안에 넣는다. 다만 **네이버에는 층 개념이
없다**(「벤치마크 경계」) — 우리는 층이 1급 정보라 개수보다 **층 분포**가 더 값지다.

### 제안

```
검색 결과 3 · 1F~2F                가까운 순 ⌄
```

- 한 층이면 `검색 결과 3 · 2F`, 여러 층이면 범위 또는 `3개 층`.
- **P의 정렬 컨트롤과 같은 줄을 쓴다.** 줄을 두 개 만들면 결과가 그만큼 밀린다.

### 실패 조건

- 층 라벨은 문자열(`B2`·`1F`)이라 **사전순으로 정렬하면 `B1`이 `1F`보다 앞에 온다.**
  범위를 적으려면 `Floor.level` 같은 순서 값이 필요한데, `StoreIndexEntry`에는
  `floorId`·`floorName`만 있고 level이 없다. → **level 없이는 범위를 적지 않는다.**
  `3개 층`으로 떨어뜨리거나, 인덱스에 level을 추가한다(응답 크기 영향 재측정 필요).
- 개수는 **서버가 준 개수인가 화면에 그린 개수인가.** 후보 목록은 상한 8로 잘려 있고
  결과 목록은 서버 상한 30이다. 잘린 목록에 전체 개수를 적으면 "3건이라는데 8줄이
  보인다"가 된다. → **그린 개수를 적고**, 잘렸으면 그 사실을 적는다.

### 검증 기준

- [x] 결과 1건일 때 머리말이 **뜨지 않는다** — `검색 결과 1 · 4F`는 바로 아래
      한 줄이 이미 말한 것을 되풀이할 뿐이다. 정렬 컨트롤과 **같은 조건**으로
      갈리므로 조건도 하나로 뒀다.
- [x] 층 범위를 적지 않는다 — `Floor.level`이 클라이언트 모델에 없어서
      `N개 층`으로 떨어뜨렸다. 층이 하나면 그 라벨을 그대로 적는다(`2F`).
- [x] 상한에 걸려 잘린 목록에서 개수가 거짓말하지 않는다 — **화면에 그린 줄**만
      센다. 묶인 시설의 나머지 층도 세지 않는다(한 줄짜리 목록에 `10개 층`이라고
      적히는 것을 막는다).

## R. 못 찾았을 때의 탈출구

### 문제

`_emptyState()`가 화면의 끝이다.

```
"xxx"에 맞는 매장을 찾지 못했어요.
다른 말로 바꿔서 다시 찾아보세요.
```

**여기서 사용자가 할 수 있는 게 없다.** 이 화면은 경량 + 의미 검색 + 온디바이스 교정을
전부 지난 뒤에만 뜨므로(설계상 맞다), 그만큼 막다른 길이라는 인상도 강하다.

우리에겐 이 자리에 놓을 재료가 **이미 있다** — 카테고리 대분류 목록(`CategoryCount`)과
최근 검색어(`recentSearchesController`)다.

### 제안

문구 아래에 **카테고리 chip 한 줄**을 얹는다. "못 찾았으니 둘러보세요"다.

```
"xxx"에 맞는 매장을 찾지 못했어요.
다른 말로 바꿔서 다시 찾아보세요.

[패션] [뷰티] [식음료] [리빙] …
```

### 실패 조건

- **"인기 검색어"는 만들지 않는다.** 로그가 없다(J절과 같은 이유).
- 카테고리를 누르면 검색 패널이 닫히고 카테고리 매장 목록 시트가 열린다 — **검색
  상태와 시트 chain이 겹치는 자리다.** `_runSheetChain`의 `_closeSheetChainRequested`
  경로를 우회하지 않는지 확인해야 한다(F절이 같은 위험을 지적했다).
- 야외에서는 카테고리 자체가 뜨지 않는다(`_indoorContextActive`). → 야외 noMatch에는
  이 줄을 넣지 않는다.

### 검증 기준

- [x] 실내 noMatch에서 카테고리 줄이 뜨고, 야외에서는 안 뜬다
- [x] chip을 눌렀을 때 상위가 그 대분류를 받는다 (패널 쪽 계약)
- [x] 카테고리를 못 받은 상태(로드 실패)에서 줄만 조용히 사라진다
- [ ] **실기기에서 시트가 실제로 열리고 검색 패널이 닫힌다** — 시트 chain은 위젯
      테스트로 재현하지 않았다. 아래 「실기기 검증」 참고.

#### 구현하며 정한 것

- **카테고리 목록을 다시 받지 않는다.** 상위(`MapShellScreen`)가 이미 들고 있는
  `_categoryEntriesFuture`를 그대로 넘긴다. 패널이 스스로 요청하면 같은 정보를 두
  번 받게 되고, 지도 위 chip 줄과 이 줄의 카테고리가 어긋날 수 있다.
- **chip을 누르면 지도 위 chip과 완전히 같은 경로를 탄다** —
  `_onSearchCategoryPicked`는 검색을 닫고 `_onCategoryChipTapped`를 부를 뿐이다.
  같은 결과에 이르는 길이 둘로 갈리면 한쪽만 고쳐지는 날이 온다.
- **로드 실패를 재시도 칩으로 드러내지 않았다.** 지도 위 chip 줄은 그렇게 하지만
  (`_CategoryRetryChip`), 여기서는 "찾지 못했어요" 화면에 오류를 하나 더 얹는
  꼴이라 줄만 조용히 사라지게 뒀다.

## S. 정확한 이름이 실재하면 형제 매장이 사라진다 <sub>실기기에서 발견 — 완료</sub>

### 문제

**실기기 검증에서 나왔다.** 1F에서 `구찌`를 치면 화면에 남는 것은 한 줄이다.

```
구찌
1F
60m · 도보 1분
```

**`구찌 뷰티`(1F)와 `구찌 선글라스`(2F)는 화면에서 사라진다.** 타이핑 중에는 후보로
셋 다 보이다가, 서버가 답하는 순간 한 줄로 접힌다. 사용자 입장에서는 방금 본 것이
사라진 것이고, 정작 `구찌 뷰티`를 찾던 사람은 여기서 길이 끊긴다.

원인은 버그가 아니라 **계약**이다. `/query/destination`은 단일 목적지 계약이라 후보를
담을 자리가 없고(`DestinationResponse`), `_is_confident_light_match`는 "최상위 tier
그룹에 서로 다른 이름이 하나뿐"이면 확정으로 본다. `구찌`는 tier 0(정확 일치) 단독
1위라 그 조건을 만족한다 — **의도대로 동작한 결과가 형제를 지운다.**

### 얼마나 되나 (시드 1640건, 서로 다른 이름 655건)

자기 이름이 다른 이름의 **접두**이기도 한 상호 — 즉 정확히 쳤을 때 형제가 가려지는
상호는 **31건(4.7%)** 이다.

```
타임(+3) · POP-UP STUDIO(+3) · 구찌(+2) · 프라다(+2)
미우미우 · 루이비통 · 시스템 · 구호 · 비비안 · A.P.C. · 노스페이스 …
```

4.7%지만 목록이 명품관 간판으로 채워져 있다. O가 고친 것과 **같은 종류의 손실**이다 —
화면이 아는 것보다 적게 말한다.

### 제안 — 서버 계약을 건드리지 않고 기기 안 인덱스로 메운다

처음에는 두 안을 놓고 고민했다.

| 안 | 내용 | 판단 |
|---|---|---|
| 1 | 서버 결과 **아래에** 온디바이스 형제를 잇는다 | **채택.** 추가 통신 0, 서버 무변경 |
| 2 | `/query/destination`에 형제 자리를 만든다 | 계약 변경이라 비싸다. 1안으로 충분하면 할 이유가 없다 |

```
[핀]   구찌                              명품
       1F
       60m · 도보 1분
───────────  이름이 비슷한 매장 2곳  ───────────
[돋보기] 구찌 뷰티                  화장품·향수
       1F
       40m · 도보 1분
[돋보기] 구찌 선글라스                아이웨어
       2F
       141m · 도보 3분
```

**정확 일치 행은 맨 위에 고정한다.** 위 화면에서 `구찌 뷰티`(40m)가 `구찌`(60m)보다
가까운데도 아래에 있다 — 사용자가 친 그 이름을 거리로 밀어내면 "이름 맞춤"이라는 말
자체가 무너진다. 그래서 **이 화면에는 정렬 컨트롤을 두지 않는다.** 머리 행이 고정된
목록은 정렬 기준 하나로 설명되지 않고, 형제는 실측 최대 3건이라 고를 것도 많지 않다.

돋보기/핀 두 아이콘이 한 목록에 섞이는 것은 네이버가 이미 쓰는 형태다
([naver-map-ui-ux-analysis.md](naver-map-ui-ux-analysis.md) 「2. 검색어 입력 중」 —
검색어 제안은 돋보기, 장소는 핀).

### 실패 조건 (먼저 정한 것)

- **무한 루프.** 형제를 탭하면 그 이름으로 재검색한다. 그 이름이 또 다른 이름의 접두
  이면 형제 목록이 한 번 더 뜰 수 있는데, 그때도 **맨 위는 정확 일치 행**이고 그 행은
  재검색이 아니라 매장으로 곧장 간다(`onStorePicked`). 어느 단계에서도 막다른 길이
  아니다. 실측으로도 **형제가 또 형제를 갖는 경우는 0건**이라 한 단계에서 끝난다.
- **카테고리로 확정된 경우.** 서버는 이름뿐 아니라 업종(tier 1)으로도 확정한다. 그때
  후보 목록에 든 것들은 형제가 아니라 이름에 질의가 든 남남이라, `이름이 비슷한 매장`
  이라고 적으면 거짓말이 된다. → **서버 결과가 후보 목록 안에 있을 때만** 만든다.
- **교정 후보.** 서버가 이미 정답을 확정한 화면에 추측을 형제라며 얹지 않는다.
- **의미 검색·discovery 결과.** 이름으로 걸린 게 아니라 형제라는 개념이 없다.
- **중복 행.** 표기만 다른 같은 이름(`물품 보관함`·`물품보관함`)을 서로 다른 매장으로
  세면 같은 줄이 두 번 그려진다. → 후보를 묶을 때 쓴 `storeMatchKey`로 맞춘다.
  이 때문에 그 함수를 공개로 바꿨다 — 정규화 규칙이 두 벌이 되면 안 된다.
- **인덱스가 없을 때.** 로드 실패·야외. 후보가 비어 있으면 지금까지의 동작 그대로다.

- [x] 형제가 더 가까워도 정확 일치 행이 맨 위다

- [x] 의미 검색 결과에는 붙이지 않는다

## 남은 문제 — 이 문서가 풀지 않는 것

**후보를 탭하면 이름으로 재검색한다.** 그래서 같은 이름이 여러 층에 있는 시설
(화장실 19곳)은 후보에서 B2를 골라도 서버가 다른 층을 확정할 수 있다. O가 대표 층을
"가장 가까운 곳"으로 고쳐도 **탭한 뒤의 목적지는 여전히 서버가 정한다.**

근본 해법은 후보에 좌표(또는 `store_id`)를 실어 바로 이동하는 것인데, K절이 응답
크기(+194KB)를 근거로 좌표를 뺐다. `store_id`는 이미 있으므로 `/places/{id}` 1건
조회로 좌표를 얻는 길이 있다 — **다음 회차 후보이고, 이 문서 범위 밖이다.**

## 확정 — 착수 전에 정하고 그대로 간 것

착수 전에는 「미결정 — 기본 제안」이었다. 하나도 뒤집지 않았으므로 **확정값**으로 옮겨
적는다. 되돌리려면 각 항목 절의 근거를 먼저 반박해야 한다.

| 결정 | 확정값 | 항목 |
|---|---|---|
| 후보 목록 정렬 | **매칭 품질순 유지** (거리는 라벨만) | O |
| 그룹 대표 선택 | **도달 가능한 것 중 최근접**, 없으면 현행 | O |
| 묶인 개수 | **도달 가능 여부와 무관하게 전체 개수** | O |
| 정렬 선택지 | **`가까운 순` · `이름 맞춤 순` 둘뿐** | P |
| 정렬 선택 저장 | **저장하지 않음** (검색어가 바뀌면 초기화) | P |
| 층 범위 표기 | **level이 없으면 `N개 층`으로 떨어뜨림** | Q |
| noMatch 탈출구 | **카테고리 대분류 chip 한 줄** | R |
| 형제 매장 | **서버 계약 무변경, 확정 행 아래에 온디바이스 형제** | S |
| 형제 화면의 정렬 | **컨트롤 없음** (머리 행이 고정이라) | S |

## 우선순위

| 순위 | 항목 | 근거 | 선행 |
|---|---|---|---|
| ✅ | **O** 후보 행 거리 + 최근접 대표 | 틀린 정보(`6F 등 19곳`)를 고치는 유일한 항목. 통신·계산 추가 0 | — |
| ✅ | **Q** 개수·층 분포 머리말 | P와 같은 줄을 쓰므로 먼저 자리를 만든다 | — |
| ✅ | **P** 정렬 기준 노출·전환 | 조용한 정렬을 드러낸다 | O·Q |
| ✅ | **R** noMatch 탈출구 | 빈도는 낮지만 막다른 길 | — |
| ✅ | **S** 형제 매장이 사라짐 | 실기기에서 발견. 서버 계약을 안 건드리고 기기 인덱스로 메웠다 | O |

**O만 유일하게 "틀린 것을 고치는" 항목이었다.** P·Q·R은 없는 것을 더하는 항목이라
순서를 미룰 수 있었지만, O는 화면이 사용자에게 잘못된 층을 알려 주고 있었다.

O~R의 자동 검증 기준은 전부 충족했다(각 절의 체크리스트). 실기기 확인은 아래에 적는다.

## 실기기 검증 (2026-08-09, Galaxy S23 · SM-S918N)

배포 Cloud Run에 그대로 붙여 확인했다. `store-index`가 이미 배포돼 있어(응답
341,135B — K절 실측표와 일치) 로컬 백엔드가 필요 없었다. 1F 에스컬레이터(ES2) 옆
복도에 위치를 찍고 확인했다.

**한글 입력을 이번에는 자동화했다.** `adb shell input text`는 여전히 비ASCII를 못 보내지만
(`%uAD6C`가 그대로 찍힌다), **화면에 뜬 삼성 두벌식 자판의 자모 키를 좌표로 두드리면**
된다. `search-input-assist.md`가 "adb로는 한글을 보낼 수 없어 자동화하지 못했다"고 적어
둔 제약은 `input text`에 한정된 것이었다.

| 확인 | 결과 |
|---|---|
| **O** 후보 행 거리 | `나이키` → 나이키스윔 `118m·도보 2분` / 나이키 골프 `145m·3분` / 나이키 라이즈 `168m·3분` |
| **O** 묶인 시설 대표 | `화` → **`화장실 · 1F 등 19곳 · 57m·도보 1분`**. 인덱스 첫 번째(6F)가 아니다 |
| **O** 개수 유지 | 대표가 1F로 바뀌어도 `19곳` 그대로 |
| **Q** 개수·층 머리말 | `검색 결과 3 · 2개 층` |
| **P** 정렬 컨트롤 | `가까운 순 ⌄` → 메뉴에 `가까운 순`·`이름 맞춤 순` 둘, 선택 반영됨 |
| **P** 타이핑 중 | 머리말·컨트롤 없이 `검색어 제안`. **거리 정렬도 안 걸린다** — `화` 후보에서 `설화수`(43m)가 `화장실`(57m)보다 **아래**에 있다(매칭 품질순) |
| **R** 탈출구 | `zzqqxv` → `카테고리로 둘러보기` + 대분류 9개. `뷰티` 탭 → 검색 닫히고 지도 강조 + 매장 목록 시트(`현재 층 · 1F 34곳`) |

**정렬 전환의 순서 변화는 실기기에서 확인하지 못했다.** `나이키` 3건은 거리순과 매칭
품질순이 우연히 같은 순서라 화면이 바뀌지 않는다. 순서가 실제로 뒤집히는 것은
`search_panel_test.dart`의 `구찌` fixture가 덮는다.

**여기서 S를 발견했다.** 위 표에 없는 것 하나 — `구찌`를 치면 결과가 **한 줄**이고
`구찌 뷰티`·`구찌 선글라스`가 사라진다. 문서를 쓸 때 "브랜드 질의는 후보 목록으로
간다"고 적었는데, 그 이름 그대로인 매장이 실재하면 서버가 자신 있게 1건을 확정한다.
위 S절에 별도 항목으로 세우고 같은 회차에 고쳤다.

### S 확인 (같은 기기·같은 위치)

| 확인 | 결과 |
|---|---|
| 형제가 붙는다 | `구찌 · 1F · 60m` 아래 `이름이 비슷한 매장 2곳` → `구찌 뷰티 · 1F · 40m` / `구찌 선글라스 · 2F · 141m` |
| 정확 일치 고정 | 형제가 **더 가까운데도**(40m < 60m) 아래에 있다 |
| 정렬 컨트롤 없음 | 머리 행이 고정된 목록이라 안 뜬다 |
| 막다른 길이 아니다 | `구찌 뷰티` 탭 → `구찌 뷰티` 1건(형제 없음) → 탭 → 상세 시트(`40m · 도보 1분`, `화장실 54m`, `엘리베이터 43m`, 출발/도착) |

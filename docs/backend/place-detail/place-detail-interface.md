## 0. 무엇을 만드는가

참고로 받은 네이버 플레이스 화면 4장은 **서로 다른 두 가지 스케일**이다.

| 화면 | 대상 | 우리 쪽 진입점 |
|---|---|---|
| 1~3 | 더현대 서울 = **건물** 홈 (개요·내부시설 500·지도 탭) | 건물을 고르거나 야외 지도에서 건물을 탭했을 때 |
| 4 | ETF베이커리 더현대서울점 = **매장** 상세 | 실내에서 매장 폴리곤·검색 결과를 탭했을 때 |

두 화면은 정보의 종류가 아니라 **범위**만 다르다. 이름·카테고리·주소/위치·영업 상태·
액션 버튼(길찾기·공유·전화·알림)·섹션 리스트라는 뼈대가 같고, 건물에는 "내부시설 500"
같은 자식 목록 섹션이 더 붙을 뿐이다. 그래서 **매장용 스키마와 건물용 스키마를 따로 만들지
않는다.** 하나의 `PlaceDetail` 계약을 두고 건물·매장·시설이 모두 그것을 구현한다.
이 문서에서 "인터페이스"라고 부르는 것은 그 계약이다.

목표 문장 하나로 줄이면: **1,640개 매장 전부가 같은 계약을 구현하고, 채워진 정보의 양에
따라 화면이 늘었다 줄었다 할 뿐 구조가 달라지지는 않게 한다.**

## 1. 현재 상태 — 지금 무엇이 없는가

### 1-1. 시트에 표시할 것이 이름과 층뿐이다

`StoreInfoSheet`는 제목(매장명), 부제(층), 카테고리 chip, 즐겨찾기 토글, 출발/도착
버튼만 그린다. 본문 자리에는 주석과 함께 빈 공간이 박혀 있다.

```dart
// store_info_sheet.dart:255
// 매장 상세 정보(사진·설명 등)는 아직 준비되지 않아 비워둔다.
const SizedBox(height: 32),
```

시트가 `initialChildSize: 0.42`로 화면 절반 가까이 차지하는데 내용은 두 줄뿐이라, 지금은
빈 여백이 그대로 보인다. 이번 작업이 채우려는 자리가 정확히 여기다.

### 1-2. 데이터 모델에 표시용 필드가 하나도 없다

`Store` 엔티티가 가진 것은 `name` / `category` / `subcategory` / 좌표(centroid·entrance) /
`polygon` / `entrance_node_id`뿐이다. 전부 **지도에 그리고 경로를 계산하기 위한** 값이고,
사람에게 읽히기 위한 값(설명·영업시간·전화·사진·특징)은 컬럼 자체가 없다.
`StoreResponse` DTO도 마찬가지다.

### 1-3. 원본(Studio)에도 없다

`backend/resources/studio/thehyundai-seoul-dabeeo/stores_*.json`이 매장의 진실 원본인데,
한 건의 모양은 이렇다.

```json
{"id": "PO-dLxzve5dF8972", "name": "MLB", "category": "매장", "subcategory": "매장",
 "floor_id": "FL-...", "entrance_local_m": {...}, "centroid_local_m": {...},
 "polygon_local_m": [...], "match": {...}}
```

원본의 `category`가 `"매장"`인 데서 보이듯 분류조차 원본에는 없고, 그래서
`store_categories.json`(id 기준)과 `store_category_by_name.json`(이름 기준)이라는 수작업
오버라이드가 따로 존재한다. 이 둘이 1,640건 전부를 덮어 런타임에는 미분류가 0건이다.
그러나 **표시용 정보(설명·특징·연락처)는 어디에서도 자동으로 나오지 않는다.** 누군가 손으로
쓰거나, 규칙으로 파생시키거나, 안 쓰거나 셋 중 하나다. 이 제약이 아래 설계 전체를 지배한다.

### 1-4. 규모: 1,640건 중 상세가 성립하는 건 539건

`stores_*.json` 11개 층 합계 1,640건인데, 그중 **1,101건(67%)이 편의시설**이고 주차구역만
787건이다. 에스컬레이터 152·엘리베이터 68을 더한 1,007건은 "설명"이라는 개념 자체가
성립하지 않는다. 실제 상세 대상은 **539건**이고 B2~6F 8개 층에 몰려 있다.
전수 조사 결과는 [wave0-coverage.md](wave0-coverage.md) 1절에 있다.

### 1-5. 클라이언트가 매장 id를 시트까지 들고 오지 못한다

`PoiSearchResult`(시트에 전달되는 모델)에 id 필드가 없다. 지도 폴리곤(`StorePolygon.id`)과
검색 응답(`QueryMatch.store_id`)에는 있는 값이 변환 과정에서 버려진다. 상세 API가 id로
조회하는 이상, 이것이 첫 번째로 풀어야 할 문제다(조사 문서 2절 B1).

## 2. 실패 조건을 먼저 정의

"잘 되는 경우"가 아니라 어디서 깨지는지부터 적는다. 이 목록이 4절 설계와 8절 검증 기준의
근거다.

**F1. 빈 껍데기 상세.** 1,640건에 필드를 열어 두고 20건만 채우면, 나머지 1,620건은
"정보가 없습니다" 카드 하나가 뜨는 화면이 된다. 지금의 빈 여백보다 나쁘다 — 지금은
"준비 중"으로 읽히지만 그때는 "이 앱은 정보가 없다"로 읽힌다.

**F2. 매장마다 다른 모양.** optional 필드를 20개 두면 A매장은 사진+설명, B매장은 전화만,
C매장은 아무것도 없는 식으로 시트 높이와 구성이 매번 달라진다. 사용자가 같은 위치에서
같은 버튼을 찾지 못한다.

**F3. 출처 없는 값이 거짓말을 한다.** 특히 **영업시간**은 시간이 지나면 자동으로 틀린
정보가 된다("영업 중"이라고 띄웠는데 닫혀 있으면 길을 헛걸음하게 만든다). 전화번호·평점도
출처 없이 넣으면 검증 불가능한 오정보다. **되돌리기 어려운 피해**(사용자 신뢰, 헛걸음)이므로
높은 위험으로 다룬다.

**F4. 원본과의 드리프트.** 수작업 JSON에 매장명을 복사해 두면 Studio에서 이름이 바뀌어도
JSON은 조용히 낡은 값을 든다. `store_category_by_name.json`이 이미 **이름을 키로** 쓰고
있어서 이 위험을 안고 있고, 조사 결과 상세 대상 539건 안에도 동명 매장이 있다(페어몬트 호텔
3건 등 — 조사 문서 1-3). 상세 오버레이는 같은 실수를 반복하면 안 된다.

**F5. 시트 chain 규약 파손.** `StoreInfoSheet`는 단순한 시트가 아니라
`_intentionalPop` / `onCloseAll` / `PopScope`로 "back은 이전 시트로, 바깥 탭·X는 전체
닫기"라는 규약을 구현하고 있고, 카테고리 목록 시트와 loop로 얽혀 있다
([map_shell_screen.dart:280](../../../client/lib/screens/map_shell/map_shell_screen.dart)).
상세 화면을 붙이면서 이 규약이 깨지면 길찾기 진입이 막힌다. **상세는 부가 기능이지만 그것이
막는 것은 핵심 기능이다.**

**F6. 페이로드·트래픽 폭증.** 상세 정보를 층 지도 응답(`FloorMapResponse`)에 끼워 넣으면
한 층 열 때마다 수백 건의 설명·이미지 URL이 따라온다. 지금 층 응답은 지도를 그리는 데
필요한 최소 묶음으로 유지되고 있고, 이 성질을 잃으면 실내 지도 첫 렌더가 느려진다.

**F7. 서버가 UI를 결정해 버린다.** (4-2에서 다룰 섹션 배열 설계의 역위험) 섹션 순서·문구를
서버가 정하면 문구 한 줄 고치는 데 백엔드 배포가 필요해진다.

**F8. 상세를 열 키가 없다.** 1-5의 문제. id를 시트까지 전달하지 못하면 API가 아무리 잘
만들어져도 호출할 수 없다. 게다가 저장한 장소는 id 없이 저장된 이력이 기기에 남아 있어
**id가 null인 경로가 영구적으로 존재**한다. 그 경로에서 시트가 깨지면 안 된다.

## 3. 목표와 비목표

### 목표

- 건물·매장·시설이 **하나의 `PlaceDetail` 계약**을 구현한다.
- 정보가 없는 매장도 **동일한 구조의 최소 화면**이 성립한다(F1·F2).
- 표시되는 모든 값에 **출처(provenance)** 가 붙는다(F3·F4).
- 상세 조회는 **별도 엔드포인트**로 분리해 층 지도 응답을 건드리지 않는다(F6).
- 기존 시트 chain 규약과 출발/도착 흐름을 **회귀 없이** 유지한다(F5).

### 비목표

- 리뷰·평점·블로그 리뷰 수 수집 (출처가 없다 — F3)
- 실시간 영업 상태 판정 (원본 없음 — F3)
- 전화 걸기·예약·공유 딥링크 **실제 연동** (버튼 자리와 계약만 잡고 동작은 후속)
- 외부 사이트 크롤링
- 1,640건 전 매장 콘텐츠 작성 (커버리지는 단계적 — 5-3)

## 4. 인터페이스 정의

### 4-1. 코어 — 모든 place가 반드시 가진 것

```
PlaceDetail
  kind          : "building" | "store" | "facility"   # 렌더러가 아이콘·기본 액션을 고르는 키
  id            : str
  name          : str
  subtitle      : str          # 매장="B2 · 베이커리", 건물="백화점"
  category      : str | null
  subcategory   : str | null
  location      : PlaceLocation
  actions       : [PlaceAction]
  sections      : [DetailSection]     # 비어 있을 수 있다
  provenance    : Provenance
```

```
PlaceLocation
  floor_label       : str | null      # "지하2층"
  building_id       : str
  position_local_m  : Point
  entrance_node_id  : str | null      # null이면 길찾기 액션을 내리지 않는다
```

```
Provenance
  source     : "studio" | "manual" | "derived"
  updated_at : date | null
  # 화면 하단에 "정보 출처/최종 확인일"로 노출. F3에 대한 방어이자,
  # 사용자가 "정보 수정 제안"을 할 근거가 된다(참고 화면 3의 그 카드).
```

**코어만으로 화면이 성립해야 한다**는 것이 이 설계의 기준선이다. `sections`가 빈 배열인
매장(=대다수)도 이름·층·카테고리·길찾기 버튼이 있는, 지금보다 나쁘지 않은 시트가 뜬다.
"정보 없음" 문구를 별도로 넣지 않는 이유가 이것이다 — 없는 것을 없다고 말하는 대신
**있는 것만 보여준다**(F1).

### 4-2. 섹션 — 있는 것만 붙는다

`sections`는 **닫힌 타입 집합**의 배열이다. 각 섹션은 자기 렌더링에 필요한 데이터를 전부
들고 있다.

| type | 내용 | 참고 화면 |
|---|---|---|
| `summary` | 한 줄 소개 (예: "소금빵보다 맛있는 버터떡의 비밀") | 4 |
| `hero` | 대표 이미지 1~n장 | 1, 4 |
| `keyValue` | 주소·위치 안내·연락처 등 라벨:값 목록 | 1, 3, 4 |
| `tags` | 특징 chip (포장·예약·문화비소득공제 등) | 1, 4 |
| `childList` | 자식 place 목록 + 카테고리별 개수 (건물의 "내부시설 500") | 2 |
| `notice` | 휴무일·팝업 기간 같은 기간성 고지 | 1 |
| `map` | 위치 미리보기 + 층 이동 안내 | 3 |

규칙 세 가지:

1. **값이 없으면 섹션을 보내지 않는다.** 빈 문자열·null·빈 배열 섹션을 만들지 않는다(F2).
2. **클라이언트는 모르는 `type`을 조용히 건너뛴다.** 서버가 새 섹션을 추가해도 구버전 앱이
   깨지지 않는다.
3. **순서는 서버가 정하고 스타일은 클라이언트가 정한다.** 서버는 "무엇을 어떤 순서로"만
   말하고, 폰트·색·간격·아이콘은 전부 Flutter 쪽 렌더러가 갖는다(F7 완화).

**왜 optional 필드 20개가 아니라 섹션 배열인가.** 필드 방식이면 클라이언트가 매장 종류마다
"이건 있나? 저건 있나?"를 20번 분기하고, 그 분기 조합이 곧 F2의 레이아웃 흔들림이다.
섹션 배열이면 클라이언트 코드는 `for (section in sections) render(section)` 한 줄이고,
"무엇을 보여줄지"의 판단이 데이터 쪽 한 곳에 모인다.

**이 선택의 대가**는 F7이다. 완화책이 위 규칙 3이고, 그럼에도 서버가 섹션 순서를 쥐는 것은
사실이다. 이 트레이드오프를 받아들이는 이유: 매장 1,640건의 정보 편차가 매우 크고, 그
편차를 흡수할 곳이 클라이언트 분기문보다 데이터가 낫다고 판단했다.

### 4-3. 건물은 같은 계약의 다른 인스턴스

더현대 서울 홈(참고 화면 1~3)은 `kind: "building"` + `childList` 섹션이다. 별도 API·별도
위젯을 만들지 않는다. 이렇게 두면 "건물 홈 → 내부시설 목록 → 매장 상세"가 같은 렌더러의
재귀가 되고, 나중에 다른 건물이 추가돼도 화면 작업이 필요 없다.

## 5. 데이터 원본

### 5-1. 원본 + 오버레이 2층 (기존 패턴 재사용)

이미 저장소에 같은 패턴이 돌고 있다 — `store_categories.json`(id 기준 분류 보정),
`store_category_by_name.json`(이름 기준 분류 보정). 세 번째로 새 방식을 만들지 않되,
**조인 키는 id만 쓴다**(F4·조사 문서 1-3).

```
backend/resources/store_details/
├─ _schema.json        ← 허용 섹션 타입·필드 선언 ("_" 접두는 오버레이가 아님)
├─ b2-food.json        ← 층·카테고리 단위로 쪼갠 수작업 오버레이
└─ ...
```

- **Studio 원본이 진실**: id·이름·층·좌표·폴리곤은 오버레이가 덮어쓰지 못한다.
- **오버레이는 표시용만**: summary·tags·keyValue.
- 오버레이의 `name`은 **사람이 diff를 읽기 위한 중복 정보**이며 조인 키가 아니다.
  조인은 항상 `id`.

### 5-2. 드리프트 검출 (F4)

검증 스크립트가 시드 시점에 세 가지를 확인하고, 하나라도 걸리면 **실패로 끝낸다**.

- 오버레이의 `id`가 Studio에 없다 → 에러 (매장이 사라졌거나 오타)
- 오버레이 `name` ≠ Studio `name` → 에러 (이름이 바뀌었으니 내용도 재확인 필요)
- `_schema.json`에 없는 섹션 타입·필드 → 에러

### 5-3. 커버리지는 단계적

전 매장 작성은 비목표다. 모집단은 조사로 확정된 **539건**이고, 우선순위는 매장 밀도가
높은 층 순이다.

1. **1차 291건** — B1(124)·4F(85)·3F(82). 손으로 작성.
2. **2차 248건** — 나머지 5개 층(B2 68·2F 64·1F 63·5F 33·6F 18).
3. **파생 92건** — 화장실·락커·교통 등 위치 안내형은 좌표·층에서 문구를 파생한다(사람이
   쓰지 않는다).
4. **제외 1,007건** — 주차·에스컬레이터·엘리베이터는 상세 시트를 열지 않는다.
5. 오버레이가 없는 매장도 코어만으로 화면이 성립한다 — 그것이 F1에 대한 답이다.

## 6. API 계약

```
GET /buildings/{building_id}/places/{place_id}
→ PlaceDetail
```

- **층 지도 응답에 넣지 않는다**(F6). 상세는 탭한 순간 1건만 가져온다.
- 응답은 `ETag` 캐시 대상. 기존 [http_cache.py](../../../backend/app/core/http_cache.py)를
  그대로 쓰고, 시드 세대(generation)가 바뀌면 무효화되는 기존 규칙에 얹는다.
- 오버레이가 없는 매장도 **200 + 코어**를 반환한다. 404가 아니다.
- 존재하지 않는 `place_id`만 404.

## 7. Flutter 화면

`StoreInfoSheet`를 확장하지 않고 **`PlaceDetailSheet`를 새로 만든 뒤 호출부를 옮긴다.**
이유: 현재 시트는 "정보 표시"와 "출발/도착 액션 반환"이 한 위젯에 섞여 있고, 여기에 비동기
로딩·섹션 렌더링·에러 상태를 더하면 F5의 chain 규약 코드가 그 사이에 파묻힌다. 규약 코드
(`_intentionalPop`·`PopScope`·`onCloseAll`)는 **그대로 복사해 유지**하고, 본문만 섹션
렌더러로 교체한다.

상태 3종을 처음부터 설계한다.

- **loading**: 코어 정보(이름·층·카테고리·출발/도착 버튼)는 검색 결과에서 이미 알고 있으므로
  **즉시 그리고**, 섹션 영역만 스켈레톤. 상세가 늦어도 길찾기는 그 순간 누를 수 있다(F5).
- **error/offline**: 섹션 영역만 조용히 비운다. 에러 다이얼로그를 띄우지 않는다 — 부가
  정보의 실패가 주 기능을 막으면 안 된다.
- **empty(섹션 0개)**: loading 종료 후 스켈레톤만 사라진다. 별도 문구 없음.

## 8. 검증 기준 (구현 전 합의)

무엇이 충족되면 "맞다"고 볼지 먼저 못 박는다.

**데이터**
- [ ] 오버레이 전 파일이 `_schema.json` 통과
- [ ] Studio에 없는 id 0건, 이름 불일치 0건 (5-2 스크립트가 CI/시드에서 실패시킴)

**백엔드**
- [ ] 오버레이가 없는 임의 매장 → 200 + `sections: []` + 코어 필드 전부
- [ ] `entrance_node_id`가 null인 매장 → 길찾기 액션이 응답에 포함되지 않음
- [ ] 층 지도 응답(`FloorMapResponse`) 필드·크기 무변화 (F6 회귀 테스트)
- [ ] 동일 요청 2회 → 두 번째가 304

**클라이언트**
- [ ] 섹션 0개 매장에서 시트 렌더 (골든/스냅샷)
- [ ] chain 규약 회귀 3종: back=이전 시트, 바깥 탭=전체 닫기, X=전체 닫기
- [ ] 상세 요청이 실패해도 출발/도착 버튼이 동작
- [ ] 상세 응답 전(loading)에도 출발/도착 버튼이 동작
- [ ] 알 수 없는 섹션 타입이 섞인 응답 → 무시하고 나머지 렌더

**성능**
- [ ] 상세 응답 p95 < 150ms (로컬, 캐시 미스)
- [ ] 이미지 lazy 로드, 시트 첫 프레임에 네트워크 이미지 대기 없음

## 9. 결정된 사항

설계 시점의 미결정 항목은 사전 조사에서 전부 답을 냈다. 근거와 숫자는
[wave0-coverage.md](wave0-coverage.md) 3절에 있고, 여기에는 결론만 적는다.

| 항목 | 결정 |
|---|---|
| 이미지(`hero`) | **이번 범위 제외.** 계약에만 남기고 서버가 내려보내지 않는다 |
| 영업시간 | **다루지 않는다.** 기간이 명시된 `notice`만 허용 |
| 시설 범위 | 주차·에스컬레이터·엘리베이터 1,007건 **제외**, 위치 안내형 92건만 파생 |
| 건물 홈 | 매장 렌더러를 먼저 세우고 같은 렌더러에 `kind: "building"`을 태운다 |
| id 없는 진입(저장한 장소) | 상세 요청을 **하지 않고** 코어만 렌더 |

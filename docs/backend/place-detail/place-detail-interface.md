## 0. 무엇을 만드는가

참고로 받은 네이버 플레이스 화면 4장은 **서로 다른 두 가지 스케일**이다.

| 화면 | 대상 | 우리 쪽 진입점 |
|---|---|---|
| 1~3 | 더현대 서울 = **건물** 홈 (개요·내부시설 500·지도 탭) | 건물을 고르거나 야외 지도에서 건물을 탭했을 때 |
| 4 | ETF베이커리 더현대서울점 = **매장** 상세 | 실내에서 매장 폴리곤·검색 결과를 탭했을 때 |

두 화면은 정보의 종류가 아니라 **범위**만 다르다. 이름·카테고리·주소/위치·영업 상태·
액션 버튼(길찾기·공유·전화·알림)·섹션 리스트라는 뼈대가 같고, 건물에는 "내부시설 500"
같은 자식 목록 섹션이 더 붙을 뿐이다. 그래서 **매장용 스키마와 건물용 스키마를 따로 만들지
않는다.** 하나의 `PlaceDetail` 계약을 두고 건물·매장·시설이 모두 그것을 구현한다.
이 문서에서 "인터페이스"라고 부르는 것은 그 계약이다.

목표 문장 하나로 줄이면: **1,640개 매장 전부가 같은 계약을 구현하고, 채워진 정보의 양에
따라 화면이 늘었다 줄었다 할 뿐 구조가 달라지지는 않게 한다.**

## 1. 현재 상태 — 지금 무엇이 없는가

### 1-1. 시트에 표시할 것이 이름과 층뿐이다

> **(해소됨 — Wave 3)** 아래는 착수 시점의 상태다. 현재는 `PlaceDetailSheet`가
> 이 자리를 섹션 렌더러로 채운다(7-A).

`StoreInfoSheet`는 제목(매장명), 부제(층), 카테고리 chip, 즐겨찾기 토글, 출발/도착
버튼만 그렸다. 본문 자리에는 주석과 함께 빈 공간이 박혀 있었다.

```dart
// store_info_sheet.dart:255 (삭제된 파일)
// 매장 상세 정보(사진·설명 등)는 아직 준비되지 않아 비워둔다.
const SizedBox(height: 32),
```

시트가 `initialChildSize: 0.42`로 화면 절반 가까이 차지하는데 내용은 두 줄뿐이라 빈 여백이
그대로 보였다. 이번 작업이 채우려던 자리가 정확히 여기다.

### 1-2. 데이터 모델에 표시용 필드가 하나도 없다

`Store` 엔티티가 가진 것은 `name` / `category` / `subcategory` / 좌표(centroid·entrance) /
`polygon` / `entrance_node_id`뿐이다. 전부 **지도에 그리고 경로를 계산하기 위한** 값이고,
사람에게 읽히기 위한 값(설명·영업시간·전화·사진·특징)은 컬럼 자체가 없다.
`StoreResponse` DTO도 마찬가지다.

### 1-3. 원본(Studio)에도 없다

`backend/resources/studio/thehyundai-seoul-dabeeo/stores_*.json`이 매장의 진실 원본인데,
한 건의 모양은 이렇다.

```json
{"id": "PO-dLxzve5dF8972", "name": "MLB", "category": "매장", "subcategory": "매장",
 "floor_id": "FL-...", "entrance_local_m": {...}, "centroid_local_m": {...},
 "polygon_local_m": [...], "match": {...}}
```

원본의 `category`가 `"매장"`인 데서 보이듯 분류조차 원본에는 없고, 그래서
`store_categories.json`(id 기준)과 `store_category_by_name.json`(이름 기준)이라는 수작업
오버라이드가 따로 존재한다. 이 둘이 1,640건 전부를 덮어 런타임에는 미분류가 0건이다.
그러나 **표시용 정보(설명·특징·연락처)는 어디에서도 자동으로 나오지 않는다.** 누군가 손으로
쓰거나, 규칙으로 파생시키거나, 안 쓰거나 셋 중 하나다. 이 제약이 아래 설계 전체를 지배한다.

### 1-4. 규모: 1,640건 중 상세가 성립하는 건 539건

`stores_*.json` 11개 층 합계 1,640건인데, 그중 **1,101건(67%)이 편의시설**이고 주차구역만
787건이다. 에스컬레이터 152·엘리베이터 68을 더한 1,007건은 "설명"이라는 개념 자체가
성립하지 않는다. 실제 상세 대상은 **539건**이고 B2~6F 8개 층에 몰려 있다.
전수 조사 결과는 [wave0-coverage.md](wave0-coverage.md) 1절에 있다.

### 1-5. 클라이언트가 매장 id를 시트까지 들고 오지 못한다

`PoiSearchResult`(시트에 전달되는 모델)에 id 필드가 없다. 지도 폴리곤(`StorePolygon.id`)과
검색 응답(`QueryMatch.store_id`)에는 있는 값이 변환 과정에서 버려진다. 상세 API가 id로
조회하는 이상, 이것이 첫 번째로 풀어야 할 문제다(조사 문서 2절 B1).

## 2. 실패 조건을 먼저 정의

"잘 되는 경우"가 아니라 어디서 깨지는지부터 적는다. 이 목록이 4절 설계와 8절 검증 기준의
근거다.

**F1. 빈 껍데기 상세.** 1,640건에 필드를 열어 두고 20건만 채우면, 나머지 1,620건은
"정보가 없습니다" 카드 하나가 뜨는 화면이 된다. 지금의 빈 여백보다 나쁘다 — 지금은
"준비 중"으로 읽히지만 그때는 "이 앱은 정보가 없다"로 읽힌다.

**F2. 매장마다 다른 모양.** optional 필드를 20개 두면 A매장은 사진+설명, B매장은 전화만,
C매장은 아무것도 없는 식으로 시트 높이와 구성이 매번 달라진다. 사용자가 같은 위치에서
같은 버튼을 찾지 못한다.

**F3. 출처 없는 값이 거짓말을 한다.** 특히 **영업시간**은 시간이 지나면 자동으로 틀린
정보가 된다("영업 중"이라고 띄웠는데 닫혀 있으면 길을 헛걸음하게 만든다). 전화번호·평점도
출처 없이 넣으면 검증 불가능한 오정보다. **되돌리기 어려운 피해**(사용자 신뢰, 헛걸음)이므로
높은 위험으로 다룬다.

**F4. 원본과의 드리프트.** 수작업 JSON에 매장명을 복사해 두면 Studio에서 이름이 바뀌어도
JSON은 조용히 낡은 값을 든다. `store_category_by_name.json`이 이미 **이름을 키로** 쓰고
있어서 이 위험을 안고 있고, 조사 결과 상세 대상 539건 안에도 동명 매장이 있다(페어몬트 호텔
3건 등 — 조사 문서 1-3). 상세 오버레이는 같은 실수를 반복하면 안 된다.

**F5. 시트 chain 규약 파손.** `StoreInfoSheet`는 단순한 시트가 아니라
`_intentionalPop` / `onCloseAll` / `PopScope`로 "back은 이전 시트로, 바깥 탭·X는 전체
닫기"라는 규약을 구현하고 있고, 카테고리 목록 시트와 loop로 얽혀 있다
([map_shell_screen.dart:280](../../../client/lib/screens/map_shell/map_shell_screen.dart)).
상세 화면을 붙이면서 이 규약이 깨지면 길찾기 진입이 막힌다. **상세는 부가 기능이지만 그것이
막는 것은 핵심 기능이다.**

**F6. 페이로드·트래픽 폭증.** 상세 정보를 층 지도 응답(`FloorMapResponse`)에 끼워 넣으면
한 층 열 때마다 수백 건의 설명·이미지 URL이 따라온다. 지금 층 응답은 지도를 그리는 데
필요한 최소 묶음으로 유지되고 있고, 이 성질을 잃으면 실내 지도 첫 렌더가 느려진다.

**F7. 서버가 UI를 결정해 버린다.** (4-2에서 다룰 섹션 배열 설계의 역위험) 섹션 순서·문구를
서버가 정하면 문구 한 줄 고치는 데 백엔드 배포가 필요해진다.

**F8. 상세를 열 키가 없다.** 1-5의 문제. id를 시트까지 전달하지 못하면 API가 아무리 잘
만들어져도 호출할 수 없다. 게다가 저장한 장소는 id 없이 저장된 이력이 기기에 남아 있어
**id가 null인 경로가 영구적으로 존재**한다. 그 경로에서 시트가 깨지면 안 된다.

## 3. 목표와 비목표

### 목표

- 건물·매장·시설이 **하나의 `PlaceDetail` 계약**을 구현한다.
- 정보가 없는 매장도 **동일한 구조의 최소 화면**이 성립한다(F1·F2).
- 표시되는 모든 값에 **출처(provenance)** 가 붙는다(F3·F4).
- 상세 조회는 **별도 엔드포인트**로 분리해 층 지도 응답을 건드리지 않는다(F6).
- 기존 시트 chain 규약과 출발/도착 흐름을 **회귀 없이** 유지한다(F5).

### 비목표

- 리뷰·평점·블로그 리뷰 수 수집 (출처가 없다 — F3)
- 실시간 영업 상태 판정 (원본 없음 — F3)
- 전화 걸기·예약·공유 딥링크 **실제 연동** (버튼 자리와 계약만 잡고 동작은 후속)
- 외부 사이트 크롤링
- 1,640건 전 매장 콘텐츠 작성 (커버리지는 단계적 — 5-3)

## 4. 인터페이스 정의

### 4-1. 코어 — 모든 place가 반드시 가진 것

```
PlaceDetail
  kind          : "building" | "store" | "facility" | "excluded"  # 렌더러가 아이콘·기본 액션을 고르는 키
  id            : str
  name          : str
  subtitle      : str          # 매장="B2 · 베이커리", 건물="백화점"
  category      : str | null
  subcategory   : str | null
  location      : PlaceLocation
  actions       : [PlaceAction]
  sections      : [DetailSection]     # 비어 있을 수 있다
  provenance    : Provenance
```

```
PlaceLocation
  floor_label       : str | null      # "지하2층"
  building_id       : str
  position_local_m  : Point
  entrance_node_id  : str | null      # null이면 길찾기 액션을 내리지 않는다
```

```
Provenance
  source     : "studio" | "manual" | "derived"
  updated_at : date | null
  # 화면 하단에 "정보 출처/최종 확인일"로 노출. F3에 대한 방어이자,
  # 사용자가 "정보 수정 제안"을 할 근거가 된다(참고 화면 3의 그 카드).
```

**코어만으로 화면이 성립해야 한다**는 것이 이 설계의 기준선이다. `sections`가 빈 배열인
매장(=대다수)도 이름·층·카테고리·길찾기 버튼이 있는, 지금보다 나쁘지 않은 시트가 뜬다.
"정보 없음" 문구를 별도로 넣지 않는 이유가 이것이다 — 없는 것을 없다고 말하는 대신
**있는 것만 보여준다**(F1).

**`excluded` kind는 구현하면서 추가했다.** 설계 초안에는 `building`/`store`/`facility`
셋뿐이었는데, 주차구역·에스컬레이터·엘리베이터 1,007건을 404로 만들면 "존재하지 않는
매장"과 "상세가 없는 매장"이 같은 응답이 되어 클라이언트가 둘을 구분하지 못한다. 그렇다고
클라이언트에 "id가 주차면 열지 마라" 같은 분류 규칙을 심으면 규칙이 두 곳에 생긴다.
`kind: "excluded"`로 200을 주고 클라이언트는 그것만 보고 시트를 열지 않는다.

### 4-2. 섹션 — 있는 것만 붙는다

`sections`는 **닫힌 타입 집합**의 배열이다. 각 섹션은 자기 렌더링에 필요한 데이터를 전부
들고 있다.

| type | 내용 | 참고 화면 |
|---|---|---|
| `summary` | 한 줄 소개 (예: "소금빵보다 맛있는 버터떡의 비밀") | 4 |
| `hero` | 대표 이미지 1~n장 | 1, 4 |
| `menu` | 메뉴 카드. 이름·사진만 필수고 카테고리·가격·용량·칼로리·카페인은 선택 | 4 |
| `keyValue` | 주소·위치 안내·연락처 등 라벨:값 목록 | 1, 3, 4 |
| `businessInfo` | 주소처럼 **잘 변하지 않는** 운영 정보 라벨:값 목록 | 1, 4 |
| `demoInfo` | 영업시간처럼 **낡는** 운영 정보. 항목마다 확인일이 붙는다(9-1 D2″) | 1 |
| `tags` | 특징 chip (포장·예약·문화비소득공제 등) | 1, 4 |
| `childList` | 자식 place 목록 + 카테고리별 개수 (건물의 "내부시설 500") | 2 |
| `notice` | 휴무일·팝업 기간 같은 기간성 고지 | 1 |
| `map` | 위치 미리보기 + 층 이동 안내 | 3 |

규칙 세 가지:

1. **값이 없으면 섹션을 보내지 않는다.** 빈 문자열·null·빈 배열 섹션을 만들지 않는다(F2).
   섹션 안의 **선택 필드도 같다** — 값이 없으면 빈 문자열로 채우지 않고 키 자체를 뺀다.
   빈 값이 실려 나가면 클라이언트가 "있는데 비었다"와 "없다"를 구분하는 분기를 갖게 되고,
   그 분기가 카드마다 다른 높이로 새어 나온다.
2. **클라이언트는 모르는 `type`을 조용히 건너뛴다.** 서버가 새 섹션을 추가해도 구버전 앱이
   깨지지 않는다.
3. **순서는 서버가 정하고 스타일은 클라이언트가 정한다.** 서버는 "무엇을 어떤 순서로"만
   말하고, 폰트·색·간격·아이콘은 전부 Flutter 쪽 렌더러가 갖는다(F7 완화).

**왜 optional 필드 20개가 아니라 섹션 배열인가.** 필드 방식이면 클라이언트가 매장 종류마다
"이건 있나? 저건 있나?"를 20번 분기하고, 그 분기 조합이 곧 F2의 레이아웃 흔들림이다.
섹션 배열이면 클라이언트 코드는 `for (section in sections) render(section)` 한 줄이고,
"무엇을 보여줄지"의 판단이 데이터 쪽 한 곳에 모인다.

**이 선택의 대가**는 F7이다. 완화책이 위 규칙 3이고, 그럼에도 서버가 섹션 순서를 쥐는 것은
사실이다. 이 트레이드오프를 받아들이는 이유: 매장 1,640건의 정보 편차가 매우 크고, 그
편차를 흡수할 곳이 클라이언트 분기문보다 데이터가 낫다고 판단했다.

### 4-3. 건물은 같은 계약의 다른 인스턴스

더현대 서울 홈(참고 화면 1~3)은 `kind: "building"` + `childList` 섹션이다. 별도 API·별도
위젯을 만들지 않는다. 이렇게 두면 "건물 홈 → 내부시설 목록 → 매장 상세"가 같은 렌더러의
재귀가 되고, 나중에 다른 건물이 추가돼도 화면 작업이 필요 없다.

## 5. 데이터 원본

### 5-1. 원본 + 오버레이 2층 (기존 패턴 재사용)

이미 저장소에 같은 패턴이 돌고 있다 — `store_categories.json`(id 기준 분류 보정),
`store_category_by_name.json`(이름 기준 분류 보정). 세 번째로 새 방식을 만들지 않되,
**조인 키는 id만 쓴다**(F4·조사 문서 1-3).

```
backend/resources/store_details/
├─ _schema.json        ← 허용 섹션 타입·필드 선언 ("_" 접두는 오버레이가 아님)
├─ b2-food.json        ← 층·카테고리 단위로 쪼갠 수작업 오버레이
└─ ...
```

- **Studio 원본이 진실**: id·이름·층·좌표·폴리곤은 오버레이가 덮어쓰지 못한다.
- **오버레이는 표시용만**: summary·tags·keyValue.
- 오버레이의 `name`은 **사람이 diff를 읽기 위한 중복 정보**이며 조인 키가 아니다.
  조인은 항상 `id`.

### 5-2. 드리프트 검출 (F4)

검증 스크립트가 시드 시점에 세 가지를 확인하고, 하나라도 걸리면 **실패로 끝낸다**.

- 오버레이의 `id`가 Studio에 없다 → 에러 (매장이 사라졌거나 오타)
- 오버레이 `name` ≠ Studio `name` → 에러 (이름이 바뀌었으니 내용도 재확인 필요)
- `_schema.json`에 없는 섹션 타입·필드 → 에러

### 5-3. 커버리지는 단계적

전 매장 작성은 비목표다. 모집단은 조사로 확정된 **539건**이고, 우선순위는 매장 밀도가
높은 층 순이다.

1. **1차 291건** — B1(124)·4F(85)·3F(82). 손으로 작성.
2. **2차 248건** — 나머지 5개 층(B2 68·2F 64·1F 63·5F 33·6F 18).
3. **파생 92건** — 화장실·락커·교통 등 위치 안내형은 좌표·층에서 문구를 파생한다(사람이
   쓰지 않는다).
4. **제외 1,007건** — 주차·에스컬레이터·엘리베이터는 상세 시트를 열지 않는다.
5. 오버레이가 없는 매장도 코어만으로 화면이 성립한다 — 그것이 F1에 대한 답이다.

## 6. API 계약

```
GET /buildings/{building_id}/places/{place_id}
→ PlaceDetail
```

- **층 지도 응답에 넣지 않는다**(F6). 상세는 탭한 순간 1건만 가져온다.
- 응답은 `ETag` 캐시 대상. 기존 [http_cache.py](../../../backend/app/core/http_cache.py)를
  그대로 쓰고, 시드 세대(generation)가 바뀌면 무효화되는 기존 규칙에 얹는다.
- 오버레이가 없는 매장도 **200 + 코어**를 반환한다. 404가 아니다.
- 존재하지 않는 `place_id`만 404.

## 7. Flutter 화면

`StoreInfoSheet`를 확장하지 않고 **`PlaceDetailSheet`를 새로 만든 뒤 호출부를 옮긴다.**
이유: 현재 시트는 "정보 표시"와 "출발/도착 액션 반환"이 한 위젯에 섞여 있고, 여기에 비동기
로딩·섹션 렌더링·에러 상태를 더하면 F5의 chain 규약 코드가 그 사이에 파묻힌다. 규약 코드
(`_intentionalPop`·`PopScope`·`onCloseAll`)는 **그대로 복사해 유지**하고, 본문만 섹션
렌더러로 교체한다.

상태 3종을 처음부터 설계한다.

- **loading**: 코어 정보(이름·층·카테고리·출발/도착 버튼)는 검색 결과에서 이미 알고 있으므로
  **즉시 그리고**, 섹션 영역만 스켈레톤. 상세가 늦어도 길찾기는 그 순간 누를 수 있다(F5).
- **error/offline**: 섹션 영역만 조용히 비운다. 에러 다이얼로그를 띄우지 않는다 — 부가
  정보의 실패가 주 기능을 막으면 안 된다.
- **empty(섹션 0개)**: loading 종료 후 스켈레톤만 사라진다. 별도 문구 없음.

## 7-A. 화면 인터페이스 명세

여기부터는 **화면에 실제로 그려지는 것**을 확정한다. 4절이 "서버가 무엇을 보내는가"의
계약이라면, 이 절은 "그 데이터가 화면에서 어떤 모양이 되는가"의 계약이다. 구현이 이 절과
다르면 구현이 틀린 것으로 본다.

### 7-A-1. 시트 골격

시트는 위에서 아래로 **고정 3영역**이다. 섹션이 몇 개든 이 골격은 변하지 않는다(F2).

```
┌────────────────────────────────────────┐
│ ① 헤더   ─ 핸들바 · X 버튼              │  SheetHeader (기존 위젯 재사용)
├────────────────────────────────────────┤
│ ② 코어   ─ 아이콘 이름 chip 저장 [출발][도착] │  네트워크를 기다리지 않는다
│           부제(층 · 세부분류)            │
├────────────────────────────────────────┤
│ ③ 본문   ─ 섹션 렌더러 세로 나열         │  loading이면 스켈레톤 1개
│                                        │
├────────────────────────────────────────┤
│ ④ 떠 있는 액션 ─ [출발][도착]           │  ②가 스크롤로 가려질 때만
└────────────────────────────────────────┘
```

- `DraggableScrollableSheet`: `initial 0.58` / `min 0.3` / `max 0.92`.
  초안의 0.42에서 올린 값이다 — 섹션이 붙으면서 빈 여백 문제(1-1)가 사라졌고, 사진이
  들어가는 매장에서 0.42는 hero만 보이고 끝난다.

**길찾기 버튼은 이름 바로 옆에 둔다.** 시트 맨 아래에 두면 상세가 길어질수록 버튼이
스크롤 저편으로 밀려나, 정작 이 앱의 주 기능이 부가 정보보다 멀어진다. 이름 옆이면
시트를 여는 순간 항상 같은 자리에 있다.

**그래도 스크롤하면 이름 행이 화면 밖으로 나간다.** 그때(스크롤 오프셋 > 92) 같은 버튼을
시트 하단에 띄운다(④). 두 위치는 같은 위젯(`_PlaceActions`)을 쓰고 같은
`StoreInfoAction`을 반환하므로, "어느 버튼을 눌렀나"가 호출부에 영향을 주지 않는다.
④가 떠 있는 동안에는 본문 아래 여백을 바 높이만큼 늘려 마지막 섹션이 가려지지 않게 한다.

②의 버튼과 ④는 **본문 상태와 무관하게 항상 활성이다.** 이것이 F5를 화면 구조로 방어하는
지점이다.

### 7-A-2. 섹션 렌더링 명세

서버가 보낸 `sections` 배열 **순서 그대로** 세로로 쌓고, 섹션 사이 간격은 `12dp` 하나로
고정한다(4-2 규칙 3 — 순서는 서버, 스타일은 클라이언트).

| type | 화면 모양 | 비어 있을 때 |
|---|---|---|
| `summary` | 흰 카드, 본문 14sp / 행간 1.45 | 카드 자체를 안 그림 |
| `hero` | 높이 220 가로 스와이프. 우하단 `n / N` 인디케이터(2장 이상일 때만) | `SizedBox.shrink()` |
| `tags` | chip `Wrap`, 파랑 배경 + 파랑 테두리. **계약에는 남아 있지만 현재 어느 매장도 쓰지 않는다** | 안 그림 |
| `menu` | 제목 "메뉴" + 카테고리 탭 + 가로 스크롤 카드(폭 172 · **높이는 글자 배율에서 계산**). 카드 = 사진 104 + 이름 + 영문명. 설명·가격·용량·칼로리·카페인은 카드를 누르면 뜨는 팝업에 | 안 그림 |
| `businessInfo` | 제목 "매장 정보" + 라벨(폭 72)·값 2열, 행 사이 Divider. **테두리·배경 없음** | 안 그림 |
| `demoInfo` | 제목 "영업 정보" + `businessInfo`와 같은 모양 + 확인일 | 안 그림 |
| `keyValue` | 흰 카드, 라벨(폭 72)·값 2열, 행 사이 Divider | 안 그림 |
| `notice` | 파랑 카드 + 확성기 아이콘, 본문 아래 "…까지" | 안 그림 |
| `map` | 파랑 카드 + 지도 아이콘, "{층} 위치" 한 줄 | 층 라벨 없으면 "지도에서 위치 확인" |
| `childList` | Wave 4에서 정의 | — |

**모르는 `type`은 파싱 단계에서 버린다.** 위젯 분기까지 오지 않는다
([place_detail.dart](../../../client/lib/models/place_detail.dart) `PlaceDetailSection.fromJson`이
`_ => null`을 반환하고 `whereType`이 걸러낸다). 위젯 레이어의 `switch`는 sealed class라
컴파일 타임에 전수 검사되고, 런타임 fallback 분기를 두지 않는다.

**이미지는 전부 앱 번들 asset이다.** `hero.local_asset`·`menu.image_asset` 모두
`Image.asset`으로 그린다. 네트워크 URL을 내려보내지 않기 때문에 시트 첫 프레임이 네트워크를
기다리지 않는다(8절 성능 기준). 등록은 파일 목록이 아니라 `assets/place_details/` 디렉터리
단위다 — 어떤 파일을 쓸지는 서버 오버레이가 정하는데, `pubspec.yaml`에 빠뜨려도 빌드는
성공하고 실행 중에 카드만 빈 채로 뜬다(메뉴를 30종으로 늘렸을 때 31개가 미등록이었다).

**메뉴 카드는 고르는 자리이고, 읽는 자리는 팝업이다.** 카드에는 이름·영문명만 싣는다. 30장을
옆으로 넘기며 훑는 화면에서 용량·칼로리·카페인 세 숫자는 이름을 가리는 노이즈였고, 그 숫자가
궁금해지는 시점은 하나를 고른 다음이다. 보여 줄 것이 없는 항목은 **누를 수 없게** 둔다 —
눌렀는데 카드에 이미 있는 이름만 다시 나오면 다음 카드도 안 누르게 된다.

팝업은 시트가 아니라 **다이얼로그**다. 상세 시트는 자기 라우트가 pop되면 `onCloseAll`로 시트
묶음 전체를 닫는데(F5), 그 위에 시트를 하나 더 쌓으면 뒤로가기 한 번이 어디까지 닫는지가
흐려진다. 다이얼로그는 별도 라우트라 뒤로가기가 팝업만 닫는다.

**카드 높이를 상수로 박지 않는다.** 230으로 고정해 뒀을 때, 기기의 글자 크기 설정이 커진
단말에서 `BOTTOM OVERFLOWED BY 2.0 PIXELS`가 떴다. 여백을 늘리는 것으로 덮으면 배율을 더 키운
기기에서 같은 일이 다시 생기므로, 글자 배율을 읽어 높이를 계산한다. 계산이 맞으려면 줄 높이가
확정돼야 해서 카드 글자에는 `TextStyle.height`를 명시한다 — 비워 두면 줄 높이가 글꼴 메트릭에서
나와 계산과 실제가 어긋난다.

**메뉴 탭은 한 항목이라도 `category`가 없으면 만들지 않는다.** 가진 것만 탭에 넣으면 나머지
항목이 어느 탭에서도 보이지 않는데, 화면에는 아무 이상이 없어 보인다. 카테고리가 한
종류뿐일 때도 만들지 않는다 — 누를 곳이 하나뿐인 탭은 아무것도 나누지 않는다.

**`demoInfo`의 확인일은 전부 같을 때만 섹션 아래에 한 번 적는다.** 같은 날짜를 항목마다
반복하면 읽히지 않는 소음이 되지만, 날짜가 다르면 묶을 수 없다 — 묶는 순간 오래된 항목이
최근에 확인된 것처럼 보인다.

### 7-A-3. 출처는 화면에 그리지 않는다

**한 번 넣었다가 뺐다.** 경위를 남겨 두는 이유는, 같은 판단이 다시 올라올 때 근거를 다시
세우지 않기 위해서다.

파일럿에서 영업시간·연락처를 넣기로 하면서(D2′) 항목마다 `source`·`confirmed_at`을 필수로
받고 화면에 `스타벅스 코리아 공식 매장 페이지 · 2026-07-30 확인` 형태로 노출했다. 시간이
지나면 틀려지는 값을 올리는 이상 확인일이 보여야 한다는 논리였다.

그 뒤 **영업시간·주차·오시는 길·위생등급을 전부 빼기로 하면서 전제가 사라졌다.**

- 영업시간을 안 다루면 "시간이 지나면 자동으로 거짓이 되는 값"이 없다.
- 오시는 길은 이미 실내에 들어와 있는 사용자에게 의미가 없다.
- 남는 것은 주소처럼 잘 변하지 않는 값이고, 여기에 확인일을 붙이면 정보량 대비 시각적
  소음만 는다.

그래서 **`provenance`와 항목별 출처를 화면에서 모두 제거했다.** 응답 계약에는 `provenance`가
남아 있다(4-1) — 데이터 쪽 추적용이며 렌더링하지 않는다.

**대신 데이터 쪽 방어는 원래 규칙(D2)으로 되돌렸다.** `forbidden_labels`가 `keyValue`와
`businessInfo` 양쪽에서 조건 없이 영업시간·연락처류를 막는다. "출처를 붙이면 통과"라는
예외가 없으므로, 출처를 화면에 안 보여줘도 검증되지 않은 값이 들어올 자리가 없다.

**그 뒤 소개 영상 때문에 전제가 되돌아왔다 → `demoInfo`만 확인일을 그린다(9-1 D2″).**
영업시간을 다시 올리기로 한 매장이 생겼으므로 "시간이 지나면 자동으로 거짓이 되는 값"이
다시 화면에 있고, 그러면 확인일이 보여야 한다는 위 논리가 그대로 성립한다. 다만 되돌린
것은 **확인일뿐이다.**

- `demoInfo`: 확인일을 그린다. 다시 열어 볼 수 있는 `source` URL은 **여전히 안 그린다** —
  그 주소가 필요한 쪽은 데이터를 고치는 사람이고, 사용자에게 필요한 것은 "언제 확인한
  값인가"다.
- `businessInfo`·`keyValue`: 그대로 아무것도 안 그린다. 주소처럼 잘 변하지 않는 값에
  확인일을 붙이면 정보량 대비 소음만 는다.
- `provenance`: 그대로 안 그린다.

두 섹션을 나눈 것 자체가 이 구분이다. 한 섹션 안에서 항목별로 확인일을 붙였다 뗐다 하면
그 분기가 곧 Wave 3.5에서 겪은 우회 경로가 된다.

### 7-A-4. 상태별 화면

| 상태 | ② 코어(이름 + 길찾기) | ③ 본문 |
|---|---|---|
| loading | 그린다 · **활성** | 스켈레톤 1개(높이 44 파랑 박스) |
| 성공(섹션 ≥ 1) | 그린다 · 활성 | 섹션 나열 |
| 성공(섹션 0) | 그린다 · 활성 | 없음 |
| 실패(500·타임아웃·오프라인) | 그린다 · **활성** | 없음 |
| `placeId == null`(구버전 저장분) | 그린다 · 활성 | 없음(요청 자체를 안 보냄) |
| `kind == "excluded"`(주차·에스컬레이터) | 그린다 · 활성 | 없음 |

④(떠 있는 액션)는 상태와 무관하게 **스크롤 위치로만** 결정된다.

**실패와 빈 결과가 화면에서 같은 모양인 것은 의도다.** 사용자에게 "정보를 못 가져왔다"와
"정보가 없다"를 구분해 줄 실익이 없고, 구분하려면 에러 문구가 필요한데 그것이 F1이다.
구분이 필요한 쪽은 개발자이므로 `frontend.log` 경고로만 남긴다.

### 7-A-5. 동작 정의

**시트 chain 규약** — F5. 기존 `StoreInfoSheet`에서 그대로 이식하며, 셋 다 회귀 테스트가 있다.

| 입력 | 동작 | 구현 |
|---|---|---|
| 뒤로(back) | 현재 시트만 닫고 **이전 시트로** 돌아간다 | `PopScope`가 `_intentionalPop`을 보고 `onCloseAll`을 호출하지 않음 |
| 시트 바깥 탭 | **전체 닫기** | 바깥 `GestureDetector` → `maybePop` → `_intentionalPop`이 false라 `onCloseAll` |
| X 버튼 | **전체 닫기** | `SheetHeader.onCloseAll` |
| 출발/도착 | 시트를 닫고 `StoreInfoAction`을 반환 | `_pop()`이 `_markIntentional()` 후 `pop(action)` — chain을 타지 않는다. **이름 옆 버튼과 하단 바가 같은 경로를 쓴다** |

시트 **내부** 탭은 빈 `GestureDetector`가 흡수해 바깥 탭으로 새지 않게 한다. 2단 구조를
유지하는 이유가 이것이다.

**상세 로딩** — `initState`에서 1회. 재시도하지 않는다.
`placeId == null`이면 요청 자체를 만들지 않는다(9절 D5). 실패는 `catch`에서 삼키고 본문을
비운다. `mounted` 검사를 거쳐 setState하므로 응답 도착 전에 시트가 닫혀도 안전하다.

**즐겨찾기 토글** — `favorite`가 주어진 경우에만 아이콘이 보인다. 토글 후 SnackBar 1.4초.
`favoritesController`를 구독해 다른 화면에서 바뀐 저장 상태가 시트에도 반영된다.

**hero 스와이프** — `PageView`. 인디케이터는 현재 인덱스만 표시하고 탭 이동은 없다.

**menu 가로 스크롤** — `ListView.separated(horizontal)`. 카드 탭 동작은 **이번 범위에 없다**
(주문·상세 페이지가 없으므로 누를 곳을 만들지 않는다).

## 9. 결정된 사항

설계 시점의 미결정 항목은 사전 조사에서 전부 답을 냈다. 근거와 숫자는
[wave0-coverage.md](wave0-coverage.md) 3절에 있고, 여기에는 결론만 적는다.

| 항목 | 결정 |
|---|---|
| 이미지(`hero`) | ~~이번 범위 제외~~ → **D1′로 갱신** (아래) |
| 영업시간 | ~~다루지 않는다~~ → D2′ 제안 → **철회** → **D2″로 갱신: 허용 목록에 든 매장만** (아래) |
| 시설 범위 | 주차·에스컬레이터·엘리베이터 1,007건 **제외**, 위치 안내형 92건만 파생 |
| 건물 홈 | 매장 렌더러를 먼저 세우고 같은 렌더러에 `kind: "building"`을 태운다 |
| id 없는 진입(저장한 장소) | 상세 요청을 **하지 않고** 코어만 렌더 |

### 9-1. 갱신된 결정 (파일럿 이후)

스타벅스 리저브 파일럿([starbucks-detail-pilot.md](starbucks-detail-pilot.md))에서 실제
출처가 확보되면서 초안의 두 결정이 바뀌었다. **결정을 바꾼 근거와 그에 딸린 방어 장치를
같이 적어 둔다** — 근거만 바뀌고 장치가 안 따라오면 그게 F3이다.

**D1′ — 이미지를 허용한다.**
초안이 이미지를 뺀 이유는 저작권·출처 불명이었다. 파일럿은 사용자가 스타벅스 코리아 공식
매장 화면에서 제공한 사진과 Pexels 무료 이미지를 쓰고, 출처·라이선스를 파일럿 문서 표에
기재했다. **원격 URL을 내려보내지 않고 앱 번들 asset 경로만 내려보낸다**(`local_asset`)는
것이 조건이다. 이렇게 하면 (a) 서버가 남의 이미지를 프록시하지 않고 (b) 시트 첫 프레임이
네트워크를 기다리지 않는다(8절 성능).

**D2′ — 영업시간·운영정보를 허용하되 출처를 강제한다. → 제안됐다가 철회됨.**

파일럿에서 공식 매장 페이지라는 출처가 생기자, `businessInfo` 항목마다
`source`·`confirmed_at`을 필수로 받고 화면에 노출하는 조건으로 영업시간·연락처를 열었다.
구현까지 갔다가 **되돌렸다.** 사유는 두 가지다.

1. **필요 없는 정보였다.** 영업시간·주차·오시는 길·위생등급을 화면에서 빼기로 하면서
   출처를 붙일 대상 자체가 사라졌다. 특히 오시는 길은 이미 실내에 있는 사용자에게 의미가 없다.
2. **출처가 있어도 낡는 것은 못 막는다.** D2′는 "검증 불가"만 해소했고 "시간이 지나면 거짓"은
   그대로였다. 확인일 만료를 강제할 기준(90일? 180일?)도 없었다.

**그래서 원래 D2로 돌아간다** — 영업시간·연락처류는 넣지 않는다. 다만 D2′를 만들다 발견한
버그 하나는 **고친 채로 유지한다**: `forbidden_labels`가 `keyValue`에만 걸려 있어
`businessInfo`가 검사를 통째로 우회했다. 검증기·시드·테스트 380건이 전부 통과하는 채로
출처 없는 `영업시간`·`대표번호`가 응답에 실려 나갔다. 지금은 두 필드 모두에서 조건 없이 막는다.

`provenance`는 응답 계약에 남지만 **화면에 그리지 않는다**(7-A-3).

**"영업 중/영업 종료" 판정 문자열을 저장하지 않는다**는 원칙은 그대로다. 저장하는 순간 그
값은 저장 시점부터 틀리기 시작한다.

**D2″ — 소개 영상용 매장 한 곳에만 영업시간을 연다(`demoInfo` + 허용 목록).**

소개 영상에 스타벅스 리저브 상세가 나오는데, 영업시간·대표번호가 없는 매장 화면은 보여 줄
것이 없었다. D2′를 되살리지 않고 **섹션을 따로 만든 이유**는 D2′가 실패한 지점이 "출처를
붙이면 통과"라는 조건부 예외였기 때문이다. 조건이 항목마다 갈리면 그 분기가 곧 우회
경로가 된다. 그래서 예외를 항목이 아니라 **필드와 매장**에 건다.

| 장치 | 내용 |
|---|---|
| 필드 분리 | `demoInfo`는 `forbidden_labels`를 적용하지 않는 **유일한** 필드다. `businessInfo`는 조건 없이 막는 규칙 그대로 |
| 매장 허용 목록 | `_schema.json`의 `demo_allowlist`에 id가 있는 매장만 쓸 수 있다. 없으면 필드가 있다는 것만으로 검증 실패 |
| 항목별 근거 | `source`(그 값이 실제로 적혀 있던 http(s) 페이지)와 `confirmed_at`(YYYY-MM-DD)이 필수 |
| 화면 | 확인일을 그린다. `source`는 안 그린다(7-A-3) |

**허용 목록이 이 결정의 핵심이다.** 이것이 없으면 "데모 전용"은 주석에만 있는 말이 되고,
검증기를 통과한다는 이유로 낡은 영업시간이 1,640개 매장에 번져 나간다. **D2′의 미해결
문제("출처가 있어도 낡는 것은 못 막는다")는 여전히 해결되지 않았다** — 확인일 만료 기준을
정하지 않았다. 목록을 한 곳으로 묶어 둔 것이 그 대신이며, 목록에 id를 더할 때는 그 매장을
실제로 확인할 사람이 누구인지도 같이 정한다.

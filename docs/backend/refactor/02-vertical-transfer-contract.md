# 02. 수직 전이(에스컬레이터/엘리베이터) 계약 단일화 — 백엔드 측

브랜치(제안): `feat/vertical-transfer-contract`

## 배경

현재 수직 이동(엘리베이터/에스컬레이터) 전이는 백엔드 그래프가 간선과 비용을 정의하지만, 클라이언트가 이름·그룹·
위치 기반으로 도착 노드를 다시 해석해 서버와 다른 결론을 낼 수 있다. 이 문서는 **백엔드가 수직 전이의 단일
원천(single source of truth)이 되도록 계약을 명시하는 작업**만 다룬다. 클라이언트에서 이름 기반 재탐색
로직(`_findArrivalNode()` 류)을 제거하는 작업은 별도 클라이언트 브랜치에서 이 계약을 소비하는 형태로 뒤따라야
한다 — 이 PR과 별개로 진행한다.

## 범위(백엔드만)

- 그래프/경로 응답 DTO에 수직 전이 endpoint를 명시적으로 포함
- `TransferMode`, `VerticalPolicy` 등 타입 도입
- 시드 단계에서 "이름 불일치는 warning으로만 기록하고 원본 topology를 기준으로 간선을 유지"하는 정책 확정

## 작업 항목

1. `backend/app/models/navigation.py`(또는 해당 Edge 모델)에서 수직 전이 간선에 다음 정보가 이미 있는지 확인하고 없으면 추가한다.
   - 사용 가능한 에스컬레이터/엘리베이터 여부
   - 단방향/양방향 여부
   - 접근성 정책
   - 실제 거리(`length_m`)와 라우팅 비용(`cost_m`) — 이미 이번 커밋에서 분리됨(유지 대상)
   - 출발/도착 노드, 적용된 전이 수단(`transfer_mode`)
2. 그래프/경로 응답 DTO(`backend/app/dto/`)에 전이 edge ID, from/to node ID, from/to floor ID, mode를 노출한다.
3. 시드 로직(`backend/scripts/seed/`)에서 이름 규칙이 원본 topology와 다를 때:
   - 전이 간선은 원본 topology 기준으로 유지
   - 이름 불일치는 warning으로 기록(별도 JSON/로그)
   - 런타임에서 이름 기반으로 endpoint를 바꾸지 않음을 코드로 보장
4. 거부된(통행 불가/방향 오류) 에스컬레이터 쌍이 위치 기반 폴백으로 다시 연결되지 않는 이번 커밋의 처리는 **유지**하고, 회귀 테스트로 고정한다.
5. API 계약 문서(`docs/backend/` 또는 OpenAPI)에 전이 필드를 반영한다.

## 완료 기준

- [ ] 그래프/경로 응답에 전이 edge ID, from/to node, mode가 포함된다.
- [ ] 서버 로그와 응답의 전이 edge ID가 항상 일치한다(같은 계산 내에서 재해석되지 않음).
- [ ] 이름 규칙 불일치가 warning으로만 기록되고 간선 자체를 바꾸지 않는다.
- [ ] 거부된 에스컬레이터 쌍이 폴백으로 부활하지 않는 회귀 테스트가 존재한다.
- [ ] 수직 이동 실제 거리(`length_m`)와 라우팅 비용(`cost_m`) 분리에 대한 회귀 테스트가 존재한다(이미 있다면 유지 확인만).

## 참고

- 원문서 3~6페이지 "P0-2. 수직 이동 경로 결정 책임 단일화", 27페이지 "Phase 1" 중 백엔드 항목.
- 클라이언트가 `transferToNodeId`를 PDR 앵커 기준으로 그대로 쓰도록 하는 작업은 클라이언트 브랜치에서 별도 진행.

# 02. 수직 전이(에스컬레이터/엘리베이터) 계약 단일화 — 백엔드 측

브랜치(제안): `feat/vertical-transfer-contract`

## 배경

현재 수직 이동(엘리베이터/에스컬레이터) 전이는 백엔드 그래프가 간선과 비용을 정의하지만, 클라이언트가 이름·그룹·
위치 기반으로 도착 노드를 다시 해석해 서버와 다른 결론을 낼 수 있다. 이 문서는 **백엔드가 수직 전이의 단일
원천(single source of truth)이 되도록 계약을 명시하는 작업**만 다룬다. 클라이언트에서 이름 기반 재탐색
로직(`_findArrivalNode()` 류)을 제거하는 작업은 별도 클라이언트 브랜치에서 이 계약을 소비하는 형태로 뒤따라야
한다 — 이 PR과 별개로 진행한다.

## 범위(백엔드만)

- 그래프/경로 응답 DTO에 수직 전이 endpoint를 명시적으로 포함
- `TransferMode`, `VerticalPolicy` 등 타입 도입
- 시드 단계에서 "이름 불일치는 warning으로만 기록하고 원본 topology를 기준으로 간선을 유지"하는 정책 확정

## 작업 항목

1. `backend/app/models/navigation.py`(또는 해당 Edge 모델)에서 수직 전이 간선에 다음 정보가 이미 있는지 확인하고 없으면 추가한다.
   - 사용 가능한 에스컬레이터/엘리베이터 여부
   - 단방향/양방향 여부
   - 접근성 정책
   - 실제 거리(`length_m`)와 라우팅 비용(`cost_m`) — 이미 이번 커밋에서 분리됨(유지 대상)
   - 출발/도착 노드, 적용된 전이 수단(`transfer_mode`)
2. 그래프/경로 응답 DTO(`backend/app/dto/`)에 전이 edge ID, from/to node ID, from/to floor ID, mode를 노출한다.
3. 시드 로직(`backend/scripts/seed/`)에서 이름 규칙이 원본 topology와 다를 때:
   - 전이 간선은 원본 topology 기준으로 유지
   - 이름 불일치는 warning으로 기록(별도 JSON/로그)
   - 런타임에서 이름 기반으로 endpoint를 바꾸지 않음을 코드로 보장
4. 거부된(통행 불가/방향 오류) 에스컬레이터 쌍이 위치 기반 폴백으로 다시 연결되지 않는 이번 커밋의 처리는 **유지**하고, 회귀 테스트로 고정한다.
5. API 계약 문서(`docs/backend/` 또는 OpenAPI)에 전이 필드를 반영한다.

## 완료 기준

- [x] 그래프/경로 응답에 전이 edge ID, from/to node, mode가 포함된다(+ from/to floor).
- [x] 서버 로그와 응답의 전이 edge ID가 항상 일치한다(같은 계산 내에서 재해석되지 않음).
- [x] 이름 규칙 불일치가 warning으로만 기록되고 간선 자체를 바꾸지 않는다 — 시드는
      원본 topology(위치 기반 매칭)로만 간선을 만들고, 이름은 방향 판정의 폴백으로만 읽는다.
- [x] 수직 이동 실제 거리(`length_m`)와 라우팅 비용(`cost_m`) 분리에 대한 회귀 테스트가 존재한다.
- [ ] 거부된 에스컬레이터 쌍이 폴백으로 부활하지 않는 회귀 테스트 — **현재 코드에는 위치
      기반 폴백 자체가 없다.** 방향별로 나눠 매칭하고 반경 밖은 `unresolved`로 남길 뿐,
      거부된 쌍을 되살리는 경로가 없다. 감사 문서가 본 커밋(main보다 앞선 브랜치)에만
      있던 로직으로 보여 이 PR에서는 추가하지 않았다.

## 적용 결과 (2026-07-30)

### 실제로 있던 문제

감사 문서는 "`length_m`/`cost_m` 분리는 이미 됐다"고 적었지만 **main에는 없었다**(그 문서는
main보다 6커밋 앞선 브랜치 기준). 실제로는 `length_m` 하나가 두 역할을 겸하고 있었다.

- 전이 간선의 `length_m`은 실제 거리가 아니라 튜닝된 라우팅 가중치였다(에스컬레이터 20m/홉,
  엘리베이터 35 + 5×홉).
- 클라이언트는 그 값을 Dijkstra 가중치로 쓰면서 **동시에** 표시 거리·총 거리로도 썼다
  (`multi_floor_router.dart`). 즉 **사용자에게 보이는 총 거리가 부풀려져 있었다** —
  실측 재시드 결과 에스컬레이터 한 칸의 실제 거리는 약 5.8m인데 20m로 계산되고 있었다.

또한 클라이언트에 이름 기반 재해석 로직이 실제로 존재한다
(~~`indoor_map_screen.dart`의 `_findArrivalNode()`~~ — **그 파일과 함수는 이후 실내 안내 리팩터에서 삭제됐다.** 아래는 당시 상태다) —
에스컬레이터 이름을 파싱해 도착 노드를 다시 고르고 `sameGroupFallback`으로 넘어간다.
**이 제거는 이 PR 범위 밖이며 후속 작업으로 남는다.**

### 바꾼 것

| 계층 | 변경 |
| --- | --- |
| 모델 | `Edge.cost_m` 추가. 층 내부 간선은 `length_m`과 같고, 전이 간선만 갈라진다 |
| 시드 | `vertical_transfers`가 실제 거리(경사면·샤프트 빗변)와 비용을 따로 계산 |
| API | 응답에 `cost_m`, `from_floor_id`, `to_floor_id` 추가 |
| 클라이언트 | Dijkstra 가중치를 `routingCostM`으로 전환. `ShortestPath`가 거리·비용을 각각 반환 |

`FLOOR_HEIGHT_M = 4.5`는 원천 데이터에 층고가 없어 둔 추정 상수다(백화점 통상값).
**라우팅 결과에는 영향이 없다** — 그쪽은 전적으로 `cost_m`이 결정한다.

### 호환성

클라이언트의 `costM`은 nullable이고 `routingCostM`이 `lengthM`으로 폴백한다. `cost_m`을
아직 안 내려주는 서버와 붙어도 층 내부 간선은 정답 그대로고(두 값이 같다), 전이 간선만
예전 동작으로 되돌아간다.

# LLM 일괄 facet 태깅 — 어휘 간극을 데이터로 메운다

작성일: 2026-07-31 (2026-08-01 갱신)

상태: **3-1 규칙분 완료 / LLM 일괄 제안은 미착수**

관련 문서: [conversational-discovery.md](conversational-discovery.md)(facet·intent 설계),
[FAISS.md](FAISS.md)(임계값·재평가 절차, W9 결과는 11-4절),
[search-qa-fix-wave.md](search-qa-fix-wave.md)

> **2026-08-01 진행 상황.** 소분류에서 결정적으로 유도되는 부분(= `rules`)은 LLM 없이
> 먼저 넣었다. intent 2개 → 7개(`신발`·`식사` + `카페`·`화장품`·`향수`·`의류`·`출구`),
> 태깅 대상 210건 → **368건**. 재평가 23/29 유지(FAISS.md 11-4절).
>
> 아래 3-1(LLM 일괄 제안)이 여전히 남아 있는 이유는, 규칙으로 유도되지 않는
> `extra_store_ids`가 사람 판단을 요구하기 때문이다 — `신발`의 145건이 그 예다.
> 3-4절 후보 중 `선물`은 소분류 규칙으로 유도되지 않아 미착수로 남았다.

---

## 1. 배경 — 병목은 코드가 아니라 커버리지다

검색 실패의 반복 원인은 **사용자 어휘와 데이터 라벨의 간극**이다.

| 사용자가 치는 말 | 데이터 라벨 | 결과 |
|---|---|---|
| `신발` | `슈즈` (소분류) | intent 연결 전에는 no_match |
| `커피` | `카페·베이커리` (복합 라벨) | tier 1 정확 일치가 못 잡음 |
| `출구` (지하철) | `지하철 5/9호선 여의도역` (B2 POI) | 이름·카테고리 어디에도 "출구" 없음 |
| `음식점` | `레스토랑`/`식음료` | no_match |

이 간극의 다리 역할인 facet/intent 층은 `feature/search-routing` 브랜치에서
**스키마·검증·시드·검색 연결까지 완성됐다.**

- 스키마: 소분류 규칙 객체 + 예외 매장 id (`_intents.json`, 12절 확정)
- 검증: `validate_intents`가 고아 id·이름 불일치·중복·죽은 규칙을 시드에서 잡는다
- 적재: 시드가 `Store.search_facets["intents"]`에 굽는다
- 검색: 경량 매칭 tier 1 + 임베딩 문서 텍스트 양쪽에서 소비한다

그러나 작성 시점에 **데이터가 1640건 중 261건, intent는 `신발`·`식사` 2개뿐이었다.**
배관은 완성됐고 물이 없었다. 남은 작업은 코드가 아니라 커버리지 확장이다.

2026-08-01 기준으로 위 표의 `커피`·`출구`·`음식점`은 규칙 + 동의어로 메웠다
(`카페` intent + `커피`→`카페`, `출구` intent + 교통 소분류, `음식점`→`식사`).

## 2. 하지 않는 것 — category/subcategory 재분류

분류 체계 자체를 갈아엎는 안은 기각한다.

1. **원인 층이 아니다.** 축이 1개뿐이라 다대다 어휘(나이키 라이즈 = 신발이자 의류)를
   담을 수 없다. 라벨을 바꿔도 간극은 다른 단어로 다시 생긴다.
2. **의존이 많다.** 클라이언트 아이콘 매핑, `styles` 파생 규칙
   (`_SUBCATEGORY_TO_STYLES`), clarify의 소분류 버킷이 전부 현재 라벨에 기대고 있다.
3. **Studio 재추출 시 원본이 돌아온다.** 원본을 고치는 대신 오버레이로 보강하는
   기존 구조(`store_categories.json` 패턴)가 맞다.

## 3. 할 일

### 3-1. LLM 일괄 제안

LLM이 1640건 전부에 `intents`(+`cuisines`)를 제안한다.

- **입력**: 매장명, 기존 category/subcategory, 상세 오버레이(`store_details/`)가
  있으면 함께.
- **출력**: 기존 `_intents.json` 스키마 **그대로**. 소분류 규칙으로 유도되는 부분은
  규칙(`rules`)에, 규칙 밖 매장만 `extra_store_ids`에. 매장별 배열 태깅은 스키마
  확정 때 기각된 방식이므로 LLM 출력도 그 형태를 쓰지 않는다
  (`store_facets.py` docstring "왜 intents는 규칙 + 예외 파일인가").
- **검증**: 기존 `validate_intents`가 고아 id·이름 불일치·규칙 중복을 그대로 잡는다.
  새 검증 코드가 필요 없다.

### 3-2. 검수는 "작성"에서 "훑기"로

기존 원칙("사람이 검수한 태그만 쓴다")은 유지하되, 사람의 일을 바꾼다 — 145건을
손으로 **작성**하는 대신, LLM이 만든 카테고리별 파일 diff를 **훑고 이상치만 제거**한다.
파일이 카테고리별로 쪼개져 있는 이유가 원래 이것이다(리뷰 단위 축소).

### 3-3. 위험도 분리

노출 위치에 따라 검수 강도를 달리한다.

- **후보 목록**(경량 매칭·임베딩 문서): LLM 태그를 즉시 사용해도 된다. 틀려도
  "목록에 한 건 더 섞임"이 피해의 상한이다.
- **`reason` 문구**("~를 위한 곳이에요"): 검수 통과분만. 사용자에게 단정적으로
  말하는 자리라 기존 원칙("추측을 사용자에게 말하지 않는다", 2절)이 그대로 적용된다.

### 3-4. intent 후보 목록 (측정으로 확인된 간극)

| intent | 근거 | 2026-08-01 상태 |
|---|---|---|
| `카페`/`커피` | `카페·베이커리` 53건이 tier 1 정확 일치 밖 | 완료 — intent `카페` 53건 + 동의어 `커피` |
| `의류` | 패션 매장 다수가 `신발`과 다대다 | 완료 — 205건 + 동의어 `옷` |
| `화장품` | 라벨은 `화장품·향수` — 정확 일치 실패 확인됨 | 완료 — 36건. **`향수`도 함께 넣어야 한다**(아래) |
| `선물` | 5-1 제안 vocabulary에 있던 값 | **미착수** — 소분류로 유도되지 않아 사람 판단 필요 |
| `지하철`/`출구` | B2 `지하철 5/9호선 여의도역` POI가 `출구` 질의에 안 걸림 | 완료 — 9건(교통 7 + facility 예외 2) + 동의어 `지하철` |
| `음식점` | `식사`와 별개의 사용자 표현 | 완료 — 동의어 `음식점`·`밥집` → `식사` |

**규칙과 동의어의 역할 분담.** 개념 하나당 intent 하나만 선언하고, 같은 개념의 다른
말은 `query_synonyms.json`에 별칭으로 넣는다. intent를 개념당 두 개 선언하면
같은 `rules`가 두 벌이 되어 한쪽만 고쳤을 때 조용히 갈린다. 예외는 `화장품`/`향수`처럼
**두 단어가 임베딩 문서 텍스트에 각각 필요한 경우**다(FAISS.md 11-4).

### 3-5. 완료 후 재평가 (필수)

`intents`가 임베딩 문서 텍스트에 들어가므로, 태깅 확장은 곧 **문서 텍스트 변경**이다.
FAISS.md 8절 절차대로:

```powershell
Set-Location backend
python -m scripts.seed.reset_and_seed
python -m scripts.evaluate_query_hybrid --baseline <이전 결과.json>
```

- 29셋 총점·질의 단위 회귀 확인
- 유효/부정 최상단 마진 재측정 → 임계값 0.50 유지 여부 판단
- 평가셋에 새 intent 질의(`커피`, `출구` 등) 추가

> 2026-08-01 규칙분 확장에서 이 절차가 실제로 회귀를 하나 잡았다 — `화장품` intent만
> 넣었을 때 `향수 보고 싶어`가 통과→실패(23→22)로 떨어졌다. 소분류 `화장품·향수`와
> 단어가 겹쳐 문서 텍스트의 무게가 쏠린 탓이다. **재평가를 건너뛰었으면 그대로
> 나갔을 회귀다.** 상세와 대응은 FAISS.md 11-4절.

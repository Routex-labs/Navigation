# 형태소 정규화 (Kiwi) — 구현 설계

[FAISS.md](FAISS.md) 4절에서 "형태소 분석기는 Kiwi로 확정하되 이번 범위는 보류"로 남긴 항목을
실제로 구현하기 위한 설계 문서다. 구현 전에 **적용 지점·실패 조건·검증 기준**을 먼저 확정한다.

> **구현 완료 상태.** `repositories/query_morph.py`를 신설했고, 각 질의 후보에
> 꼬리 제거 → 형태소 정규화를 적용한다. 후속 보강으로 문장 끝 구두점 후보, 공백-only `422`,
> AI 경로의 모호한 부분 일치 → FAISS 분기까지 반영했다. FAISS 내부 전처리와 임계값은 그대로다.

## 1. 해결할 문제

경량 1차 매칭(`repositories/query_search.py`)의 질의 정규화가 **하드코딩된 꼬리 목록**이다.

```python
_TAILS = ("몇 층이야", "몇층이야", "몇 층", "몇층", "어디야", "어디", "위치", "알려줘")
```

- 목록에 없는 조사·어미는 못 벗긴다: `"화장실이"`, `"스타벅스는"`, `"엘리베이터까지"`, `"화장실 급해"`.
- 꼬리를 **최대 1개만** 제거한다: `"화장실 어디야"`는 `"어디야"`만 떨어져 `"화장실"`이 되지만,
  `"화장실이 어디야"`는 `"화장실이"`가 남아 `_tier`의 정확 일치(tier 0)·카테고리 일치(tier 1)에서 모두 빠진다.
- 부분 일치(tier 2)가 `q in name` 방향이라 **질의가 더 길면 매칭이 끊긴다**. 조사가 붙는 순간
  `"화장실이" in "화장실"` 은 거짓이다. 즉 조사 하나로 1차가 통째로 비고 2차(임베딩)로 넘어간다.
- 2차로 넘어간다는 건 **torch 로드 + 임베딩 인코딩 비용**을 조사 하나 때문에 치른다는 뜻이다.
  게다가 `query_search.match_destination`·`match_info`(일반 검색·정보 질의)에는 2차가 없어서,
  그쪽은 그냥 `no_match`가 된다.

완료 조건(Definition of Done):

- 조사·어미가 붙은 자연어 질의가 **1차 경량 매칭에서** 잡힌다(임베딩 없이).
- 기존 응답 계약(`dto/query.py`)과 기존 테스트가 그대로 통과한다.
- Kiwi가 없는 환경에서도 서버는 기동하고, 기존 `_TAILS` 규칙으로 동작한다(품질만 하락).

## 2. 범위

- **이번 범위** — `query_search`의 질의 후보를 형태소 기반으로 정규화. 브랜드 사용자 사전 등록.
  `match_destination` / `match_info` / `match_ai_destination` 1차가 모두 이득을 본다(공유 함수).
- **범위 밖** — 임베딩 문서 텍스트(`query_semantic._document_text`) 변경. 인덱스 텍스트를 바꾸면
  FAISS 임계값의 튜닝 근거가 무효가 된다(FAISS.md 8절). 별도 작업으로 재평가와 함께 한다.
- **범위 밖** — 임계값·리랭커·동의어 사전 확장.
- **범위 밖** — 클라이언트 변경. 서버 내부 매칭 품질 개선이라 API 계약이 그대로다.

## 3. 설계

### 3.1 적용 지점

```
질의 텍스트
   │
   ▼
_query_candidates() ── 원문 + 문장 끝 구두점 제거 후보
   │
   ▼
_strip_tail() → query_morph.normalize()
   │
   ├─▶ 동의어 사전(canon)          ── 그대로
   └─▶ _tier() 매칭                ── 그대로
```

원래 Kiwi 적용은 정규화 함수에 국한했다. 후속 검증에서 문장 끝 구두점과 공백 입력,
AI 경로의 모호한 tier 2를 발견해 후보 생성·라우터 검증·AI 오케스트레이션도 보강했다.

### 3.2 정규화 규칙 — 실제 분석 결과로 두 번 수정됨

초안은 "명사만 뽑아 공백으로 이어 붙인다"였다. 실제 Kiwi 출력을 찍어 보고 **두 군데가 틀렸다.**

**(가) 토큰을 이어 붙이면 안 된다 → 원문 스팬에서 제거만 한다.**

```
"가게A 어디야" → [('가게',NNG,0,2), ('A',SL,2,1), ('어디',NP,4,2), ('이',VCP), ('야',EF)]
```

공백으로 join하면 `"가게 A"`가 되어 이름 정확 일치(tier 0)가 깨진다. 공백 없이 join하면
`"TAX REFUND"` → `"TAXREFUND"`로 또 깨진다. **원문의 문자 위치를 유지한 채 제거 대상 스팬만
공백으로 덮고 공백을 정리**하는 방식만이 둘 다 살린다.

**(나) 명사 허용 목록으로는 "몇 층이야"를 못 뗀다 → 꼬리 제거를 앞단에 유지한다.**

```
"화장실 몇 층이야" → [('화장실',NNG), ('몇',MM), ('층',NNG), ('이',VCP), ('야',EF)]
```

`"층"`은 일반명사(`NNG`)라 명사 필터를 통과한다 → `"화장실 층"`. 기존 `_TAILS` 꼬리 제거를
**폴백이 아니라 1단계 전처리로도** 남겨 `"몇 층이야"`를 먼저 떼고, 그다음 형태소가 남은 조사를 뗀다.

최종 규칙:

1. `_query_candidates()` — 원문 후보를 먼저 두고, 문장 끝의 연속된 `? ! . ,` 등을 한 글자씩
   모두 제거하며 후보를 추가한다. 원문이 먼저라 `"A.P.C."` 같은 실제 상호는 정확
   일치가 우선하고, `"A.P.C.?"`도 다음 후보에서 찾는다. 빈 후보는 버린다.
   HTTP 요청과 저장소 함수 모두 200자 상한으로 후보 생성 비용을 제한한다.
2. 각 후보에 `_strip_tail()` — 기존 `_TAILS` 꼬리를 최대 1개 제거
   (`"화장실 몇 층이야"` → `"화장실"`).
3. `query_morph.normalize()` — Kiwi로 분석해 **제거 대상 태그의 스팬만** 지운다.
   제거: `J*`(조사) `E*`(어미) `V*`(용언) `MM`(관형사 "몇") `MA*`(부사) `NP`(대명사 "어디")
   `XSV`/`XSA`(용언파생접미사). 그 외는 남긴다.
4. **허용 목록이 아니라 제거 목록인 이유**: 모르는 태그는 남기는 쪽이 기존 동작에 가깝다.
   실제로 `"B1 주차"`의 `"주차"`는 `NNB`(의존명사), `"애들"`의 `"들"`은 `XSN`으로 분석된다 —
   명사 허용 목록(`NNG`/`NNP`)만 썼다면 둘 다 잘려 나갔다.
5. **남는 게 없으면 꼬리 제거 결과로 폴백.** 분석기가 다 날려도 기존 동작으로 떨어진다.
6. 결과는 소문자화(`_norm`)해 기존 비교 규칙과 동일하게 맞춘다.

### 3.3 브랜드 오분해 방지 — 동의어만으로는 부족했다

초안은 `query_synonyms.json`의 키·값 16건만 사용자 사전에 등록하는 것이었다.
**전 매장 전수 측정에서 이게 부족하다는 게 드러났다.** 미등록 고유명사는 끝음절이 조사로 오인된다.

| 매장명 | 등록 전 | 오인된 태그 |
|---|---|---|
| 리모와 | `리모` | `와` → 접속조사(JC) |
| 생로랑 | `생로` | `랑` → 접속조사 |
| 발렌시아가 | `발렌시아` | `가` → 주격조사(JKS) |
| 미도 | `미` | `도` → 보조사(JX) |
| 더 캐시미어 | `캐시미어` | `더` → 부사(MAG) |

**원문 질의인데도 깨지는 회귀**가 1531건 중 35건이었다. 그래서 동의어뿐 아니라
**매장명 전체를 사용자 사전에 등록**한다(`query_morph.register_words`, `_rank`가 호출).
고유 659건 등록에 1ms 미만이고, 이미 등록된 단어는 건너뛰므로 두 번째 요청부터는 사실상 무료다.

> **등록 순서 의존성.** 데이터에 `"물품 보관함"`과 `"물품보관함"`이 둘 다 있다. 붙임 표기를
> 먼저 등록하면 Kiwi가 띄어쓴 쪽을 `물품+보관+하+ㅁ`으로 쪼갠다(`score`로도 안 바뀜).
> 현재는 리스트 순서상 띄어쓴 쪽이 먼저라 문제없고, 뒤집혀도 부분 일치로 매칭은 유지된다.
> 근본 해결은 Studio 데이터에서 표기를 하나로 합치는 것이다.

### 3.4 실패 시 폴백

Kiwi는 **선택 의존성**으로 다룬다. `query_semantic._get_model()`과 같은 패턴이다.

- `import kiwipiepy` 실패 / 인스턴스 생성 실패 → 플래그를 세우고 **기존 `_TAILS` 규칙으로 폴백**.
- 분석 중 예외 → 해당 질의만 원본 텍스트로 폴백(서버는 죽지 않음).
- 인스턴스는 지연 로드 싱글턴 + 락. 요청마다 새로 만들지 않는다.

## 5. 실패 조건 — 먼저 짚어 둔다

- **한글+영문 붙은 이름**: `"가게A"`가 `"가게 A"`로 벌어지면 tier 0이 깨진다 → 3.2 (가) 스팬 방식으로 방어.
- **영문·숫자 시설명**: `"TAX REFUND"`(`SL SL`), `"B1 주차"`(`SL SN NNB`)가 보존돼야 한다.
  제거 목록 방식이라 통과하지만, 목록을 늘릴 때 다시 깨질 수 있다 → 회귀 테스트로 고정했다.
- **한 글자 매장명**: 명사 추출 후 한 글자만 남으면 일반 검색의 tier 2 부분 일치가 과매칭될 수 있다.
  AI 경로는 서로 다른 이름이 여럿이면 FAISS로 넘기지만 `destination`·`info`의 규칙은 유지한다.
- **동의어 키가 명사로 안 잡히는 경우**: `"스벅"`, `"엘베"`, `"마뗑킴"` → 3.3 사용자 사전으로 방어.
- **Kiwi 미설치 환경**: 폴백이 동작하는지 monkeypatch로 재현해 테스트했다.
- **성능**: Kiwi 인스턴스 최초 생성 비용(수백 ms). 지연 로드 싱글턴이라 첫 질의만 부담한다.
- **여전히 1차에서 안 잡히는 것**: `"밥 먹을 데"` → `"밥 데"`, `"애들 신발"` → `"애들 신발"`.
  개념 검색이라 형태소로는 안 되고 임베딩(2차)의 몫이다. 2차에는 **원문 그대로** 넘어가므로
  2차 자체의 임베딩 점수에는 영향을 주지 않는다.
- **문장 끝 구두점 — 해결**: 원문 후보를 보존한 채 끝 구두점을 단계적으로 제거한다.
  `A.P.C.`·`We,pet` 보존, `? ! . ,` 문장 변형, Kiwi 폴백까지 회귀 테스트로 고정했다.
- **공백뿐인 요청 — 해결**: 세 요청 모델이 strip 후 빈 값이면 `422`를 반환한다.
  검증을 통과한 원문은 응답 `query`에 그대로 보존한다.
- **AI 1차/2차 선택 변화 — 해결**: 최상위 tier 2에 서로 다른 매장명이 둘 이상이면
  ID순 경량 후보를 확정하지 않고 원문을 FAISS로 넘긴다. 2차도 실패하면 `no_match`다.

### 6.1 전수 검사 — 무엇을, 왜 그렇게 재는가

`tests/unit/test_query_coverage.py`가 `resources/studio/stores_*.json`에서 **이름만** 읽어
전 매장을 훑는다(DB 시딩 없음, 2.2초). 통계 정리는 `backend/notebooks/kiwi_eval.ipynb`.

- **`_rank`가 아니라 `_query_candidates`를 본다.** `_tier`의 정확 이름 일치(tier 0)는
  후보 중 하나가 `_norm(매장명)`이면 성립한다. 전 매장 × 전 변형을 `_rank`로 돌리면 매 질의가
  1531건을 훑어 O(n²)가 되지만, 후보 포함 여부를 비교하면 같은 것을 증명하면서 선형에 끝난다.
- **받침에 따라 조사를 고른다.** `"펜디이 어디야"`는 비문이다. 받침 없는 이름엔 `가/는`,
  있는 이름엔 `이/은`을 붙인다. 이걸 안 했던 초기 측정은 실패 430건을 잘못 보고했다.
- **영문·숫자로 끝나는 이름(`MLB`, `7A`)에는 조사 변형을 적용하지 않는다.**
  따라서 7개 변형 중 원문·공통 꼬리 5종은 1531개 전부, 조사 2종은 한글로 끝나는
  645개에만 적용한다(`1531 × 5 + 645 × 2 = 8945`).

**측정 코드가 두 번 거짓말했다** — 받침을 안 따진 비문 변형이 없는 실패 430건을 만들었고,
`set()` 순회 순서가 없는 실패 1건(`물품 보관함`)을 만들었다. 수치를 믿기 전에 질의 문법과
입력 순서를 먼저 고정해야 한다.

## 7. 남은 작업

- Studio 데이터의 표기 중복 정리(`"물품 보관함"` / `"물품보관함"`) — 3.3의 순서 의존성이 사라진다.
- 일반 검색의 tier 2 한계: `"여자 화장실"` 같은 다중 명사 질의는 아직 1차에서 안 잡힌다.
- 임베딩 문서 텍스트에도 형태소를 적용할지는 FAISS 임계값 재튜닝과 함께 판단.
- 29개 기대 패턴에서 놓친 질의(배고픔·가방·ATM·짐 보관 등)는 매장 설명/동의어를
  임베딩 문서에 넣은 뒤 임계값과 함께 다시 측정한다.
- 스레드 안전성: 사전 추가와 분석을 락으로 묶었지만 **필요함이 증명되진 않았다**(음성 대조군에서
  실패 미재현, kiwipiepy는 스레드 안전성 미문서화). 처리량이 문제되면 재검토.

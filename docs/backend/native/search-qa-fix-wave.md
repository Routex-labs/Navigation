# 검색 예외 질의 QA — 수정 Wave 계획

작성일: 2026-07-29

상태: Planning

관련 문서: [conversational-discovery.md](conversational-discovery.md)(전체 설계 배경),
[FAISS.md](FAISS.md), [query.md](query.md)

`feature/query-ai` 브랜치를 로컬(Chrome + uvicorn)로 띄워 "검색하면 안 나올 만한 질문"을
직접 던져본 QA 라운드의 결과다. 여기서 나온 실패·오탐 사례를 근거로 Wave 1~4로 고친다.
각 Wave는 `conversational-discovery.md`가 이미 잡아 둔 미결정 항목(12절)과 겹치므로,
그 문서의 해당 절 번호를 함께 표기한다.

## 0. QA 라운드 — 오탐 잡기

### 방법

**1단계 (완료):** `run_probe_light.py`로 `/query/destination`만 55개 질의 + 층 스코프 6케이스.
→ 결과: `results_light.json` ✓

**2단계 (부분 완료):** `run_probe.py`로 destination + ai 전체 배치.
- **Destination 호출**: 65건 모두 연결 거부 (서버 준비 시간 초과)
- **AI 호출**: 37건 성공 기록, 2건 타임아웃
- **Floor scope**: 미실행 (destination 실패로 스킵)

**근본 원인**: Backend job 시작 후 uvicorn이 8001 포트에 바인드되는 데 30초를 초과했다.
Health check 타임아웃 후 probe 스크립트가 계속 진행했지만 destination 호출은 모두 실패.
그 사이 backend가 점차 준비되면서 ai 호출(나중 단계)은 성공하기 시작했다.
**타이밍 이슈지 코드 결함이 아니다.** 다음 실행에서는 대기 시간을 60초로 늘린다.

### 확정된 실패 사례

| 그룹 | 질의 | 결과 |
|---|---|---|
| 카테고리 통칭어 | 화장품, 신발, 운동화, 가방, 시계, 속옷, 골프웨어, 술, 빵, 아동복, 장난감, 병원, 환전, 짐보관, 분실물, 고객센터, 발렛, 택시, 셔틀버스, 스포츠 | `no_match` |
| 오타 | 나이크, 스타벅수, 탬버린쯔 | `no_match` (기대대로 — 퍼지 매칭 없음) |
| 자연어 | 배고파, 아이랑 놀만한 곳, 선물 사려고, 옷 사고싶어, 밥 먹을 데, 쉴 곳 있어, 담배 피울 곳 | `no_match` (1차 경량 기준 정상. `/query/ai` 2차 의미 검색 검증은 미완료) |

### 확정된 오탐(false positive) 사례 — Wave 4 대상

| 질의 | 기대 | 실제 매칭 | 원인 추정 |
|---|---|---|---|
| `샤낼`(샤넬 오타) | 샤넬 뷰티 또는 no_match | `샤브미담`(레스토랑) | `query_morph` 정규화 또는 부분 문자열 매칭이 의도치 않은 후보에 걸림 |
| `물 사고싶어` | no_match 또는 생수 판매처 | `물품보관함`(락커) | tier 2 이름 부분 일치가 "물" 한 글자로 걸림 — `_name_match_rank`의 `_CONTAINS` 등급이 너무 관대함 |
| `1`, `...`, `a` | no_match | 각각 `1C`(주차구역), `P.A.3`(주차구역), `ARKET CAFE` | 한두 글자·구두점만 남는 질의가 임의 매장에 걸림. `_query_candidates`가 짧은 후보를 걸러내지 않음 |

이 사례들은 `query_search.py`의 tier 2(`_CONTAINS`, `_name_match_rank`)가 최소 길이 제한 없이
부분 문자열이면 무조건 후보로 인정하기 때문이다. Wave 4에서 최소 질의 길이 또는 자모 수
기준을 추가한다.

### 핵심 발견 — `/query/ai`(2차 의미 검색)는 이미 대부분 해소한다

37건의 AI 배치 결과 중 **destination(1차)에서 no_match였던 카테고리 통칭어 대부분이
AI 2차에서 정확히 해결됐다.**

| 질의 | destination(1차) | `/query/ai`(2차) |
|---|---|---|
| 신발 | no_match | ok → **탠디**(subcategory `슈즈`, 정확) |
| 운동화 | no_match | ok → 나이키 라이즈 |
| 가방 | no_match | ok → 포터 |
| 시계 | no_match | ok → 브라이틀링 |
| 속옷 | no_match | ok → 비너스 |
| 골프웨어 | no_match | ok → 브리핑 골프 |
| 술 | no_match | ok → 신동와인 |
| 빵 | no_match | ok → 블랑 케이크 |
| 아동복 | no_match | ok → 오프레임 |
| 병원 | no_match | ok → 메이린 클리닉 |
| 스포츠 | no_match | ok → 나이키스윔 |

AI로도 끝까지 `no_match`인 것: 장난감, 환전, 분실물, 발렛, 택시, 셔틀버스 — 이 여섯은
건물에 해당 서비스·매장이 실제로 없을 가능성이 높다(데이터 부재 vs 검색 결함 구분 필요,
Wave 2 범위 밖).

**이게 Wave 2의 결론을 바꾼다.** "신발 → 나이키/아디다스가 안 뜬다"는 문제는 매칭 자체가
안 되는 게 아니라 — 의미 검색은 이미 올바른 후보(탠디)를 top-1으로 찾아낸다 — 다음 두
문제로 좁혀진다.

1. **클라이언트가 AI를 안 부른다.** `conversational-discovery.md` 1-2절이 이미 지적한
   대로, 상단 검색은 "경량이 빈손 + 엔터 확정" 조건에서만 AI를 호출한다. 타이핑만으로는
   최종 "결과 없음"이 먼저 뜬다. 즉 사용자가 실제로 겪는 "신발 검색해도 안 나옴"은
   상당 부분 **AI가 아예 안 불려서**다.
2. **여러 브랜드 노출은 여전히 불가능.** AI도 top-1만 반환하므로(`match` 단일 필드),
   설사 잘 불려도 탠디 하나만 나오지 나이키·아디다스가 함께 나오지는 않는다. 이 부분만
   Phase 1·2(facet·다중 후보 계약)가 필요하다.

**완료 (2026-07-30):** 전체 배치 재실행 완주 — 서버 죽지 않음, destination 65건 +
ai 65건 + 층 스코프 7건 전부 기록(`results.json`). 집계: destination ok 28 / no_match 40,
ai ok 51 / no_match 17. Wave 4 수정 후 오탐 5건(`샤낼`·`물 사고싶어`·`1`·`...`·`a`)은
destination에서 전부 no_match로 회귀 확인. 층 스코프 7건 전부 정상(층 지정 시 해당 층,
미지정 시 B6 기본).

남은 관찰 1건: `"1"` 질의가 `/query/ai`(2차 의미 검색)에서는 여전히 `1C`(주차구역)를
반환한다. Wave 4는 경량 경로(tier 2 길이 하한)만 고쳤고 의미 검색 경로는 별도라 예상된
동작이다. 의미 검색의 무의미 질의 방어는 FAISS.md의 임계값 논의(`asdfqwerzxcv` 0.458)와
같은 주제이므로 Phase 2에서 다룬다.

## Wave 1 — 층 스코프: `current_floor_id`를 클라이언트가 안 보낸다

### 증상

`화장실`처럼 시설 질의를 하면 항상 B6 결과가 나온다(사용자 보고). 현재 층과 무관하다.

### 원인 (백엔드 로그로 확정)

`query_search._load_stores`는 `current_floor_id`가 오면 정확히 그 층으로 필터링한다 —
`1F`~`B2`까지 직접 넣어 재현하면 전부 해당 층 화장실이 정확히 나온다. 하지만 이
파라미터를 안 보내면 전체 건물에서 `(floor.level, store.id)` 정렬 첫 매장이 뽑히고,
그게 우연히 B6다. 즉 **백엔드는 정상이고, 클라이언트가 `current_floor_id`를 안 보낸다.**

`conversational-discovery.md` 1-3절 표가 이미 이 구조를 문서화했다:

| 호출부 | `current_floor_id` |
|---|---|
| `search_panel.dart` (상단 검색) | 보내지 않음 |
| `ai_search_sheet.dart` (경로 안내 화면 FAB) | 현재 층을 보냄 |

즉 상단 검색에서 "화장실"을 치면 무조건 이 문제가 재현되고, 경로 안내 화면 FAB에서
물으면 재현되지 않아야 한다(교차 확인 필요 — 8-1 참고).

### 변경 범위

- `client/lib/widgets/search_panel.dart` — 검색 요청 조립부에 현재 층 상태를 실어 보낸다.
  현재 층을 어디서 읽어오는지는 `outdoor_map_screen.dart`/`indoor_map_screen.dart`의 층
  상태 소스를 따라간다(신규 상태를 만들지 않는다).
- 백엔드 계약은 이미 `current_floor_id: str | None`을 받으므로 **백엔드 변경 없음.**
- `conversational-discovery.md` 8-2절의 미결정 A/B 선택도 이 김에 확정한다 — 기본안(A:
  tier 0·1 시설 질의는 층 스코프 유지)을 그대로 채택하면 이번 수정과 정합적이다.

### 검증 기준

- [ ] 1F에서 "화장실" 검색 → 1F 화장실이 나온다(2F, B1 등에서도 동일하게 교차 확인).
- [ ] `ai_search_sheet.dart` 쪽은 기존처럼 계속 현재 층을 보낸다(회귀 없음).
- [ ] `client/tests/unit_test/`에 층 스코프 회귀 테스트 추가.

## Wave 2 — "신발" 같은 통칭어가 여러 브랜드를 안 보여준다

### 증상 (사용자 보고 + QA 확인)

"신발"로 검색하면 나이키·아디다스가 안 뜬다. 브랜드명으로 직접 치면(나이키, 아디다스,
뉴발란스) 전부 정확히 뜬다 — 즉 데이터·이름 매칭 자체는 문제 없다.

### 원인 — 세 겹 (0절 AI 배치 결과로 갱신)

0절에서 확인했듯 `/query/ai`(2차 의미 검색)는 "신발" → 탠디(정확한 슈즈 매장)를 이미
찾아낸다. 즉 매칭 자체는 문제가 아니다. 실제 원인은 다음 세 가지다.

1. **1차 경량 매칭 실패는 예상된 동작:** "신발"은 어떤 store의 `category`/`subcategory`와도
   문자열이 정확히 같지 않다(subcategory는 `슈즈`). tier 1에 걸리려면 질의가 그 문자열과
   완전히 같아야 한다(`query_search._tier`). 이건 애초에 2차 의미 검색이 받아야 할 몫이고,
   실제로 받고 있다 — **문제가 아니다.**
2. **(우선순위 최상) 클라이언트가 AI를 안 부른다:** `conversational-discovery.md` 1-2절 —
   상단 검색은 "경량 빈손 + 엔터 확정" 조건에서만 AI를 호출한다. Phase 0 항목이자
   이 문제의 실제 병목. **먼저 이것부터 고친다.**
3. **여러 브랜드 노출은 응답 계약의 구조적 한계:** `/query/destination`·`/query/ai`는
   `match` 단일 필드만 반환한다(`dto/query.py`). AI가 탠디를 top-1으로 잘 찾아도 나이키·
   아디다스가 함께 나오는 건 지금 API 모양으로 불가능하다. Phase 1·2가 필요한 부분은
   여기부터다.

`conversational-discovery.md`가 이 문제 전체(다중 후보 응답, tier 1 과잉 확정, 신발
브랜드가 `슈즈`가 아니라 `캐주얼·스트리트`로 분류된 데이터 현실)를 이미 1-1·1-4·1-5·
4-2절에서 다루고 있고, Phase 1(facet 시범)·Phase 2(백엔드 탐색 계약)가 이 문제를 위한
설계다. **즉 Wave 2는 새로 설계하지 않고 그 문서의 Phase 1 잔여 작업 + Phase 2 착수로
푼다.**

### 변경 범위 — 순서대로

**2-a (즉시, 작음): 클라이언트가 AI를 부르게 한다.** `conversational-discovery.md`
Phase 0 항목 그대로다.
- `client/lib/widgets/search_panel.dart` — 의미 검색을 `submitTick`(엔터) 하나에
  의존하지 말고 debounce 종료 시에도 태운다. 경량 결과가 있어도(현재는
  `results.isNotEmpty`면 건너뜀) 스킵하지 않는다.
- 타이핑 중 경량이 빈손이라는 이유만으로 최종 `"결과 없음"` 문구를 띄우지 않는다.
- 이 조각만으로도 "신발 → 탠디" 정도는 실제 사용자에게 노출된다(top-1이지만 no_match보다
  훨씬 낫다). 별도 API 계약 변경이 필요 없다.

**2-b (큼, 병행 가능): 여러 브랜드 노출 — Phase 1 잔여 + Phase 2 착수.**
- `conversational-discovery.md` 11절 진행 상태 표의 잔여 262건 검수 중 **P2(슈즈 8건
  styles)·P3(패션 "신발 취급 여부" 196건)** 를 먼저 끝낸다.
- `backend/resources/store_search_facets/` 오버레이 파일에 신발 관련 매장 태깅 반영.
- Phase 2 최소 버전: `_is_confident_light_match`를 tier 1까지 확장(1-4)하고,
  `DiscoveryResponse`(8-3안) 최소 버전으로 `clarify`/`results` 모드를 얹는다.

### 검증 기준

- [ ] (2-a) 타이핑만으로 "신발"을 치면(엔터 없이) AI 호출이 실제 발생하고 탠디가 노출된다.
- [ ] (2-a) AI 호출 전에는 최종 `"결과 없음"` 문구가 뜨지 않는다.
- [ ] (2-b) "신발" 질의가 `clarify` 또는 `results`로 응답하고, 나이키·아디다스·탠디 등
      서로 다른 브랜드가 함께 포함된다.
- [ ] `conversational-discovery.md` 10절 백엔드 검증 기준 중 "신발" 관련 항목과 동일선상.

## Wave 3 — `search_facets` 컬럼이 전부 비어 있다

### 증상 (DB 직접 확인)

`stores` 테이블 1640건 전부 `search_facets`가 `NULL`(또는 문자열 `"null"`)이다.
`seed_navigation.py`는 `store.get("search_facets")`를 그대로 컬럼에 넣는 구조라 로더
자체는 정상이지만, **원본 오버레이 JSON에 실제 태그가 없어서** 매 건 빈 값이 들어간다.

### 원인

`conversational-discovery.md` 11절이 이미 이 상태를 정확히 기록해 뒀다 — "파생 규칙·
오버레이 로더·검증기·시드 배선까지 완료. 남은 것은 사람 검수 262건." 즉 배선(코드)은
끝났고 **데이터(오버레이 JSON 파일 내용)가 비어 있다.** Wave 2의 P2·P3 검수가 끝나면
이 컬럼도 자동으로 채워진다 — Wave 3는 별도 코드 작업이 아니라 **Wave 2 검수 작업의
결과 확인 단계**로 좁힌다.

### 변경 범위

- 별도 코드 변경 없음. `backend/resources/store_search_facets/*.json` 오버레이 파일에
  검수된 태그를 채우는 작업(Wave 2와 동일 작업).
- 완료 후 `python -m scripts.seed.reset_and_seed`로 재시딩하고, DB에서
  `search_facets IS NOT NULL`인 행 수가 검수 건수와 일치하는지 확인한다.

### 검증 기준

## Wave 4 — 오탐 두 건 + 짧은 질의 오매칭 수정

### 증상 (0절 QA 결과)

- `샤낼`(샤넬 오타) → `샤브미담`으로 오매칭.
- `물 사고싶어` → `물품보관함`으로 오매칭.
- 한 글자/구두점만 남는 질의(`1`, `...`, `a`)가 무관한 매장에 걸림.

### 원인 (코드 확인)

`query_search._tier`의 tier 2 분기가 `_name_match_rank`를 거치는데, 이 함수는
`q in name`이면 최소 길이 제한 없이 무조건 `_CONTAINS` 등급으로 인정한다
(`query_search.py:109-116`). `_query_candidates`도 구두점을 한 글자씩 벗기며 후보를
늘리기만 하고 벗긴 결과가 너무 짧아지면 후보에서 빼는 하한이 없다.

`샤낼` 건은 별도로 `query_morph.normalize`/동의어 사전 어느 단계에서 뒤틀리는지
재현 로그를 먼저 뜬 뒤 원인을 좁힌다 — 지금은 "이런 사례가 있다"만 확정됐고 정확한
경유 지점은 미확인이다.

### 변경 범위

- `backend/app/repositories/query_search.py` — tier 2 `_CONTAINS` 등급에 최소 질의
  길이(예: 자모 2자 미만 제외) 하한을 추가.
- `샤낼` 재현: `_query_candidates("샤낼")`·`_normalize_variant`·`_synonyms()` 각 단계
  출력을 찍어 어디서 `샤브미담`과 연결되는지 확인 후 해당 단계 수정.
- 회귀 방지용 유닛 테스트를 `tests/unit/test_query_search.py`에 추가(오탐 케이스 그대로).

### 검증 기준

- [ ] `샤낼` → `no_match` 또는 `샤넬 뷰티`(둘 중 하나로 확정, 팀 논의 후 결정).
- [ ] `물 사고싶어` → `no_match` 또는 실제 생수 판매 매장(있다면).
- [ ] `1`, `...`, `a`처럼 실질 정보가 없는 질의는 `no_match`.
- [ ] 기존 tier 2 정상 케이스(`"이" → "이솝"`, `"A.P.C."` 등)는 회귀 없음
      (`tests/unit/test_query_search.py` 기존 스위트 통과).

`conversational-discovery.md`(전체 설계)와 이 문서(QA 결과)를 겹치면 결론은 하나다.

```text
Track A (백엔드 코드)   : W5-a ─┬─→ W6 ──→ W7

Track B (데이터 검수)   : W8-a → W8-b → W8-c → W8-d   (각각 끝날 때마다 W9 반복)

Track D (운영 품질)     : W14 (전부 이후)
```
